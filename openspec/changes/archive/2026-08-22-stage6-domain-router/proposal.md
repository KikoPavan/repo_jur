## Why

The FROZEN architecture requires the Stage 6 Domain Router: the deterministic, post-Quality-Gate selection of exactly one of the three route targets `legal_knowledge`, `judicial_process`, or `review_required`, without hidden semantic classification (`technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §3.2, §8B, §18 Stage 6; `implementation-plan-repo-jur-v1.1-FROZEN.md` §8; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §1; acceptance criteria §17 #25 and #30; `implementation-plan-correction-impact-v1.0-FROZEN.md` §4 — "Domain Router conservador"). Stage 4 (Critical-Data Validation) and Stage 5 (Phase 1 Quality Gate) are already implemented and are explicitly domain-neutral: neither constructs, imports, or assigns a route target, and both specs declare that the downstream routing decision belongs to this stage (`openspec/specs/critical-data-validation/spec.md` Requirement "Critical-Data Validation introduces no domain-routing decision"; `openspec/specs/phase1-quality-gate/spec.md` Requirement "Quality Gate introduces no domain-routing decision"; `decision-memo-phase1-quality-gate-v1.0-FROZEN.md` §1 — the gate "não decide identity/routing"). No component in the current repository produces a domain-routing decision: `RouteTarget` exists in `src/pipeline_juridico/contracts.py:113-116` as an unused shared contract (its only consumer today is the `guard_legal_bundle_write` signature and `tests/test_contracts.py`), `router.py` is the page-level routing seam (per-page `Metodo` classification) and must not be touched, and there is no routing observability and no operational route command. The Domain Router seam must be created, consuming the Stage 3/4/5 boundary outputs, exactly as Stage 4 and Stage 5 each added their seam, and it must remain a pure, deterministic, non-mutating decision over conformant Phase 1 artifacts.

Human review decisions (2026-08-22, task t_4bfbe485 comment thread) are incorporated as normative authorities for this change:

- **HR-1 — `legal_hints` is NOT authorized as a routing authority in Stage 6 v1.** No `legal_knowledge` or `judicial_process` route may be derived from `legal_hints`. A future OpenSpec change may authorize deterministic `legal_hints` rules if normative authority is established.
- **HR-2 — workflow context IS approved and MUST be instantiated as the initial explicit routing signal**, as a minimal deterministic contract: `requested_domain = legal_knowledge | judicial_process`. This is explicit workflow/operator intent, not semantic inference from document content.
- **HR-3 — a routing context that violates its contract is a configuration error** (`RoutingConfigurationError`), never `review_required`; `review_required` is reserved for valid input with no authorized decisive signal or other permitted ambiguity.

## What Changes

- Add the Stage 6 Domain Router as a domain-neutral, deterministic, non-mutating routing seam that runs strictly after the Phase 1 Quality Gate, consumes the Phase 1 artifacts read-only plus the Critical-Data Validation status and a validated routing context, and returns exactly one of the three `RouteTarget` outcomes — `legal_knowledge`, `judicial_process`, `review_required` (serialized values; already the shared contract in `src/pipeline_juridico/contracts.py` — **no change to `contracts.py`**).
- Reuse the existing `RouteTarget` enum and the existing `Phase1Artifacts` boundary type; create a minimal `src/pipeline_juridico/domain_router.py` module (physical-layout memo: no suitable existing implementation produces a domain-routing decision — `router.py` is page-level routing under a different contract and is explicitly out of scope for modification) exposing a pure, stateless entry point over the artifacts plus a frozen decision envelope.
- Enforce the FROZEN precedence exactly (`implementation-plan-repo-jur-v1.1-FROZEN.md` §8): the recorded Quality Gate outcome must be `PASS` or `PASS_WITH_WARNINGS` for routing to proceed; a recorded `FAIL` means **stop** — routing does not occur and no routing decision is produced; a Critical-Data Validation status of `REVIEW_REQUIRED` routes to `review_required` before any routing signal is evaluated.
- Define the initial permitted routing signal contract per the approved human decision (HR-2): the validated routing context carries exactly one permitted signal — `requested_domain`, whose value is exactly one of `legal_knowledge` or `judicial_process` (explicit workflow/operator intent; never derived from document content). Evaluation follows the approved fixed order: (1) recorded gate `FAIL` → stop; (2) critical `REVIEW_REQUIRED` → `review_required`; (3) `requested_domain == legal_knowledge` → `legal_knowledge`; (4) `requested_domain == judicial_process` → `judicial_process`; (5) `requested_domain` absent → `review_required`. `legal_hints` is **excluded** from the permitted vocabulary (HR-1): collector candidate hints never select a domain, even when a future change approves them as signals it will be a new, separate grant of authority. Any routing context that violates the fixed contract (unrecognized key, invalid value) raises the dedicated `RoutingConfigurationError` (HR-3) — never a silent `review_required`, never a domain route.
- Add routing observability as an operational/technical artifact only: one deterministic JSON record per routing execution, stored outside the canonical bundle and outside Phase 1 content, under a configurable operational directory (default `var/routing/state/`), never containing document content or full critical identifier values, and recording routing-signal **presence (keys) only, never values** (routing metadata belongs to operational/technical artifacts per tech spec §3.2/§8B; observability stays outside `/bundle/` per §15).
- Add the minimal operational route command `repo-jur route` (C6.2) as a new console script (`src/pipeline_juridico/domain_router_cli.py`), following the FROZEN §14 operational-CLI surface recommendation (`repo-jur <verb>`; command naming is Implementation Choice) and the existing CLI conventions (argparse, environment-driven directories, sanitized logging, deterministic exit codes). The command exposes an explicit `--domain legal_knowledge|judicial_process` flag consistent with the approved `requested_domain` contract (approved human decision). The existing `converter-juridico` CLI is **not** modified (CLI non-regression).
- Enforce the FROZEN boundaries: the router never performs semantic classification or LLM calls, never enriches, never generates YAML, never behaves as a Producer, never publishes, never writes to `/bundle/` or to process storage, never invokes `guard_legal_bundle_write` (that guard remains the Stage 7/8 producer-boundary authorization), never mutates the Phase 1 Markdown (byte-identical before/after), and never touches `router.py` page-routing semantics.
- Do not implement Stage 7 (Legal Semantic Review/Producer), Stage 8 (Process Semantic Review/Producer), Stage 9 (Retrieval), domain schemas, or publication; do not change the converter, OCR provider, page routing, cleaner, validator, report generation, Stage 4/5 code, dependencies, or FROZEN authorities.

## Capabilities

### New Capabilities

- `domain-router`: Defines the domain-neutral Stage 6 boundary that runs strictly after the Phase 1 Quality Gate, receives only conformant Phase 1 artifacts (read-only) plus the Critical-Data Validation status and a validated routing context, and selects exactly one of the three `RouteTarget` outcomes — `legal_knowledge`, `judicial_process`, `review_required` — following the approved precedence (recorded gate `FAIL` stops routing; Critical-Data `REVIEW_REQUIRED` routes to `review_required`; only the single explicitly permitted deterministic signal `requested_domain` — explicit workflow/operator intent, values `legal_knowledge` or `judicial_process` — may select a domain; `requested_domain` absent routes to `review_required`; contract-violating context raises a dedicated configuration error), without hidden semantic classification, document-content inference, enrichment, YAML generation, Producer behavior, publication, Phase 1 body mutation, or any write to canonical bundle/process storage, and with routing metadata confined to a dedicated operational/technical observability artifact plus a minimal operational route CLI.

### Modified Capabilities

None.

The existing `contract-harness`, `itp-ingress-preflight-evidence`, `shared-conversion-core`, `critical-data-validation`, `phase1-quality-gate`, and `juridical-pdf-conversion` requirements are not changed by this proposal.

## Non-Goals

- Approving any routing signal beyond the single approved `requested_domain` signal — in particular, no `legal_hints`-derived rule (HR-1: not authorized in Stage 6 v1) and no additional workflow-context field. Approving additional signals is a future, separate change.
- Implementing Stage 7 (Legal Knowledge Semantic Review / Producer) or Stage 8 (Judicial Process Semantic Review / Producer), including any use of `guard_legal_bundle_write` or any canonical/process-storage write — the router only *selects* the route; downstream stages consume it.
- Implementing Stage 9 (Legal Knowledge Retrieval) or any Judicial Process retrieval.
- Creating Legal OKF / Process YAML or enrichment schemas, or coupling the router to any domain schema (shared-conversion-core memo *Prohibited Coupling*).
- Modifying `router.py` page-routing semantics, the converter, OCR provider, routing thresholds, cleaner, validator, report generation, Stage 4/5 code, or the `converter-juridico` CLI.
- Changing `contracts.py` (`RouteTarget`, `guard_legal_bundle_write`, `Phase1Artifacts`, shared state enums) or `config.py`'s bundle-boundary enforcement.
- Adding or changing dependencies.
- Writing to `repo_jur/bundle/` or to process-domain storage.

## Residual Risks

1. **The `requested_domain` signal is trusted operator intent; the router cannot detect a caller that derives it from document content.** The approved contract (HR-2) defines the signal as explicit workflow/operator intent, never semantic inference. The router itself only reads the validated routing context (and the CLI `--domain` flag that maps onto it) and never reads the Markdown body; the spec forbids content-derived signals and a source-inspection test asserts the router contains no content-analysis path. If a future pipeline component derives `requested_domain` from document content, that would be hidden classification *before* the router — outside this capability's authority to detect; the mitigation is the spec prohibition plus the source-inspection test.
2. **The routing-context carrier is a new technical artifact with no FROZEN-mandated schema.** The `requested_domain` contract is approved by human decision (HR-2), but its carrier (validated JSON context / CLI flag) is this change's design (Decision 4 in `design.md`), constrained by the FROZEN input classes of impl plan §8 ("workflow context" among them). Any future extension of the carrier (additional workflow-context fields) is a new, separate change.
3. **The Critical-Data Validation status is not recorded in the Phase 1 technical report.** Stage 4 implemented the seam (`CriticalDataValidator.validate`) but the report schema (`Relatorio` / `report.py`) does not carry its result; the router therefore receives the critical status as an explicit pipeline parameter. If a future report-schema change records the critical status (the §14.3 report synchronization tracked by Stage 5), the router may later read it from the report without architectural change. The router does not read any non-existent field today.
4. **The routing observability record has no FROZEN-mandated schema.** Tech spec §15.1 enumerates ingress/Phase-1/producer/retrieval events but no routing event; §15.2 requires only that log location be configurable outside the bundle. The record shape in `design.md` (Decision 8) is therefore an OpenSpec design decision constrained by §15.3 (no secrets/content in logs) and §3.2/§8B (routing metadata stays in operational/technical artifacts). The spec defines behavioral constraints, not the concrete field names.
5. **"Conflicting routing signals" is normative but not executable under the initial single-signal vocabulary.** With exactly one permitted signal (`requested_domain`), two approved signals cannot conflict; the conflict rule (conflict → `review_required`) is stated in the spec per the task invariant "missing, conflicting, or ambiguous routing signals route to `review_required`" and becomes executable only when a future change approves a second signal. The spec scenario is written against the evaluation procedure, and the executable tests cover every state reachable under the single-signal vocabulary.
6. **The `repo-jur` console script and the `--domain` flag extend the operational surface without FROZEN-mandated names.** Tech spec §14 names the `repo-jur <verb>` surface as *recommended* and command naming as Implementation Choice; the flag-to-signal mapping (`--domain` → `requested_domain`) is this change's design, and the existing `converter-juridico` surface is untouched (CLI non-regression proven by tests).

## Impact

- Primary affected code: new `src/pipeline_juridico/domain_router.py`, new `src/pipeline_juridico/domain_router_cli.py`, new `tests/test_domain_router.py`, new `tests/test_domain_router_cli.py`, and one new console-script entry (`repo-jur`) in `pyproject.toml`; no existing module is modified.
- `Phase1Artifacts` (Stage 3 output) and the recorded Quality Gate result (Stage 5 wiring) become the routing input contract; the literal Markdown and the technical report remain byte-identical before and after routing.
- `RouteTarget` (already defined in `src/pipeline_juridico/contracts.py`) becomes the routing outcome contract; `guard_legal_bundle_write` remains the Stage 7/8 write-authorization guard and is not invoked by the router.
- `CriticalValidationStatus` (Stage 4) is consumed read-only by the router; Stage 4 itself is unchanged and its existing independence tests keep passing.
- New operational surface: `repo-jur route <markdown> <report.json> [--domain legal_knowledge|judicial_process] [--context <context.json>] [--state-dir <dir>] [--log-level <level>] [--json]` with a routing-observability record written under a configurable operational directory (default `var/routing/state/`), outside the canonical bundle and Phase 1 content.
- No new dependency, storage provider, service, database, credential, canonical bundle write, or domain-specific schema is introduced.
- Stage 7/8/9 remain out of scope and are not coupled to by this change.
