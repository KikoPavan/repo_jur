## Why

Stage 4 now exposes the Critical-Data Validation seam behind `CriticalDataValidator.validate(phase1_artifacts, profile) -> CriticalValidationResult`, which is explicitly independent of the physical Quality Gate decision (`decision-memo-critical-data-validation-runtime-semantics-v1.0-FROZEN.md`; `implementation-plan-repo-jur-v1.1-FROZEN.md` §7 *Independence*). The FROZEN architecture still requires the Phase 1 Quality Gate itself: the deterministic, engine-neutral evaluation of the physical conversion output that decides exactly `PASS`, `PASS_WITH_WARNINGS` (serialized value; human label "PASS WITH WARNINGS"), or `FAIL` and gates the handoff to the OKF Producer (`decision-memo-phase1-quality-gate-v1.0-FROZEN.md`; `phase1-operational-spec-v1.1-FROZEN.md` §7–§16; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §6.3, §8.5, §17 criteria #6–#7 and #25, §18 Stage 5; `external-source-ingestion-contract-v1.6-FROZEN.md` §6.6 and §7; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §8.9 and invariants 22–23).

The current repository has no component that produces the FROZEN gate states. `GateState` exists as an unused shared contract in `src/pipeline_juridico/contracts.py:82-85` (the shared-conversion-core bounded-contexts memo lists "Quality Gate states" among the shared contracts), the converter's internal validators (`src/pipeline_juridico/validator.py`) raise exceptions against the raw converter output (markers adjacent to `<!-- método: ... -->` comments), and `report.determine_final_status` returns `StatusExecucao` (`sucesso`/`incompleto`/`falha`) — an execution-status concept distinct from the three normative gate states. The Quality Gate seam must be created as a read-only deterministic evaluation over the Shared Conversion Core boundary output (`Phase1Artifacts`), mirroring how Stage 3 and Stage 4 each added their seam, and it must remain strictly independent of the Stage 4 `CriticalValidationResult` and of the Stage 6 Domain Router.

## What Changes

- Add the Stage 5 Phase 1 Quality Gate seam as a domain-neutral, non-mutating deterministic evaluation consuming the Stage 3 `Phase1Artifacts` (literal Markdown + technical conversion report) and returning a gate result whose state is exactly one of the three `GateState` members: `PASS`, `PASS_WITH_WARNINGS`, `FAIL` (serialized values; the second member's human label is "PASS WITH WARNINGS" — the label is never a serialized value, and the serialized value is never used as a human label).
- Reuse the existing `GateState` enum already shaped per the FROZEN three-state contract in `src/pipeline_juridico/contracts.py`; no change to `contracts.py`.
- Create a minimal `src/pipeline_juridico/quality_gate.py` module (physical-layout memo: no suitable existing implementation produces gate states, so a new module is justified; existing `validator.py` helpers are NOT reused because they validate the raw converter output under a different textual contract — markers with adjacent method comments — while the boundary literal carries markers only) with a pure, stateless evaluation entry point `evaluate(phase1_artifacts) -> QualityGateResult` and a frozen `QualityGateResult` dataclass (`state: GateState`, `warnings: tuple[str, ...]`, `errors: tuple[str, ...]`, optional non-authoritative `diagnostics`).
- Implement the deterministic fatal-rule set and warning taxonomy exactly as supported by the FROZEN corpus: page integrity (exactly N markers `1..N`, no missing/duplicate/out-of-order marker, no silently ignored page), extraction outcome (page whose report record is not completed/error-state — including a page whose `pages[].method` is `erro`, fatal independently of its `pages[].status` per memo §3.3/§6 criterion 4/§8.2 — and empty return on a page not determined blank — the empty-return rule is its own deterministic fatal rule and is NOT a stand-in for a "known truncation" check), structural/textual conformance (UTF-8, no NUL bytes, no CR line endings, no technical method comment in the literal body, parseable technical report with minimum required fields), report failure (missing evidence SHA-256, missing page count, incomplete page inventory — exactly `source.pages` page records whose page numbers are exactly the set `{1..N}`, with no missing, duplicated, out-of-range, or extra page numbers; record order is not normative because no FROZEN baseline defines it), and the explicit prohibition of implicit heuristic thresholds as fatal rules. A "known truncation" check is NOT implemented: the memo's `truncamento conhecido` criterion (§8.2/§3.4; op-spec §7.1/§7.3; tech spec §17) is a normative FATAL condition — an explicit, authoritative truncation signal produces FAIL — but the current technical report contract (`Relatorio`) defines no truncation signal, so no artifact produced under the current contract can present one and the condition cannot be evaluated today; the gate must not infer truncation from other observable signals or equate it with the empty-return rule. The absent signal is recorded as a residual (below), not invented (determination: not a blocker, because the gate evaluates only observable artifact signals and no conformant artifact on the current contract can present a truncation signal).
- Implement the PASS / PASS_WITH_WARNINGS / FAIL semantics of `decision-memo-phase1-quality-gate-v1.0-FROZEN.md` §5–§8 and `phase1-operational-spec-v1.1-FROZEN.md` §7: successful OCR is compatible with `PASS` and is never a warning by itself; a legitimately blank page (report `method: vazia`) keeps its marker and is not a warning; `PASS_WITH_WARNINGS` (serialized value; human label "PASS WITH WARNINGS") requires complete conformant output plus at least one non-fatal warning recorded in the report; `allow_partial` is NEVER itself a FAIL condition and NEVER waives an independently detected fatal condition — `FAIL` derives solely from the underlying unresolved page-level error (report `pages[].status` not completed, or `pages[].method` equal to `erro` — each independently fatal), the gate reads no partial-output flag and exposes no waiver mechanism.
- Enforce strict independence from Stage 4: the Quality Gate never constructs, imports, or assigns a `CriticalValidationResult`/status/finding, and a `REVIEW_REQUIRED` critical-data status does not alter the physical gate outcome (the downstream `review_required` combination mapping belongs to the Stage 6 Domain Router per `implementation-plan-repo-jur-v1.1-FROZEN.md` §8 *Precedence* and is explicitly NOT implemented here).
- Enforce no coupling to Stage 6 and no production authority: no domain-routing target is constructed/imported, no canonical bundle write occurs, no `verified`/OKF `status` is created or mutated; the gate reports eligibility only.
- Add the non-mutation invariants as executable tests: `SHA256(markdown_before) == SHA256(markdown_after)` and byte-identical technical report across the evaluation call.
- Add a domain-neutrality and independence source-inspection test mirroring `tests/test_conversion_engine.py:298-306` and the Stage 4 pattern, asserting the new module never references Critical-Data Validation types, `RouteTarget`, or bundle storage.
- Do not implement Stage 6 Domain Router, Semantic Review, Producers, canonical publication, or retrieval; do not change the converter, OCR provider, routing, cleaner, validator, report generation, CLI, or Stage 4 code; do not add or change dependencies; do not write to `repo_jur/bundle/`.

## Capabilities

### New Capabilities

- `phase1-quality-gate`: Defines the domain-neutral Stage 5 boundary that consumes the Shared Conversion Core output (literal Markdown + technical conversion report), evaluates physical quality and conformance deterministically, and returns a gate result whose state is exactly one of the three `GateState` members — `PASS`, `PASS_WITH_WARNINGS` (human label "PASS WITH WARNINGS"), `FAIL` — plus gate-owned warnings/errors, without mutating the literal Markdown or the technical report, without assigning a Critical-Data Validation status, and without any routing, publication, or lifecycle decision. None.

The existing `shared-conversion-core`, `critical-data-validation`, `itp-ingress-preflight-evidence`, `contract-harness`, and `juridical-pdf-conversion` requirements are not changed by this proposal.

- Introducing any heuristic threshold (mojibake ratio, confidence, character statistics) as a fatal rule — no such threshold is frozen in the corpus.
- Adding or changing dependencies.
- Writing to `repo_jur/bundle/`.

## Residual Risks

These gaps exist in the FROZEN corpus or in the current repository and are not resolved by invention in this change:

1. **The current Phase 1 technical report schema does not implement the FROZEN §6.3 minimum block layout.** `Relatorio` (`src/pipeline_juridico/models.py` + `report.py`) carries `run_id` (not `execution_id`), flat `source` fields (`path`, `size_bytes`, `sha256`, `pages`) instead of `input.{sha256,byte_size,page_count}`, no `phase1` block, no `result.{quality_gate,warnings,errors}` block, no `artifacts.{markdown_sha256}`, no `telemetry`, and per-page records named `number`/`method`/`status`/`characters`/`warnings`/`error` instead of `page_number`/`char_count`/`warnings`/`errors`. The Quality Gate memo §14.3 and tech spec §6.3 require this synchronization; the current report was already REUSED as "the Technical JSON schema" by Stage 4. This change therefore maps the existing field names onto the FROZEN concepts inside the gate (one isolated mapping, Decision 8), and records the schema synchronization as a separate follow-up, rather than rewriting the report (which would modify report generation and the converter's emitted artifact — out of Stage 5 scope).
2. **No frozen "known truncation" signal exists in the current report contract; this is a documented residual, not a blocker and not a waiver of the normative rule.** The memo's `truncamento conhecido` FAIL condition (memo §8.2, §3.4; op-spec §7.1/§7.3; tech spec §17) is normative: an explicit, authoritative signal in the report that the output was truncated is fatal. The current `Relatorio` schema defines no such field, so no artifact produced under the current contract can present a truncation signal and the condition cannot be evaluated today. The gate therefore implements NO known-truncation check, never infers truncation from other observable signals, and does NOT equate it with the empty-return rule, which is its own deterministic fatal rule (a page whose `pages[].status` is completed but whose method is not `vazia` with `characters == 0` ⇒ FAIL, per memo §9.3/§8.2 and op-spec §7.3). The §14.3 report synchronization must add the executable check — an explicit frozen truncation flag — before the already-normative condition becomes evaluable on the report contract; the gate would then consume it as a fatal signal without changing its architecture. This is an already-normative deferred-evaluability requirement, preserved in the design (Decision 6) and the spec, not a waiver. This is the same class of corpus/implementation gap as residuals 1 and 3 and does not prevent deterministic implementation of every observable rule.
3. **`artifacts.markdown_sha256` cannot be verified at the gate today.** The existing `output.sha256` hashes the raw converter output (with method comments), while the boundary literal is normalized by Stage 3 (comments stripped), so a hash comparison would false-FAIL conformant boundary output. The gate performs no markdown-hash comparison; the report synchronization (risk 1) must redefine the markdown hash over the boundary output before any such comparison can be performed by the gate.
4. **`technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §16.1 lists Quality Gate unit tests but the current converter's internal raise-based validation is embedded and engine-coupled**; this change adds the gate tests required by §17 criteria #6/#7/#25/#30 as a standalone seam, without touching the embedded validation.
5. **No FROZEN baseline defines `[[TEXTO ILEGÍVEL]]` (or any other illegible-text sentinel) as a canonical marker.** The marker exists only as a current-implementation constant (`cleaner.py:7`) and in the non-frozen design doc; the Quality Gate memo §16.10 explicitly removed it as a mandatory sentinel created by that memo, and tech spec §8.4 states "This specification does not create a mandatory `[ilegível]` sentinel". The gate therefore defines no marker-based warning rule. Source illegibility is registered through the report record (page `method: erro` / `status` not completed / `warnings`), which the extraction-outcome fatal rule already handles deterministically; under `allow_partial` the marker appears only on pages already in error state (converter.py:606-607), so no additional gate rule is needed or warranted.
6. **The current technical report contract exposes no authoritative signal for "known semantic alteration or invention" (memo §6 criterion 11; op-spec §7.2 "zero perda conhecida de conteúdo").** The gate inputs define no observable signal for that criterion, so the spec excludes it from the implemented PASS rule set and the gate implements no such detection; this gap is documented here — matching the spec's existing statement — rather than resolved by invention. Any report-recorded technical condition (including a suspected semantic alteration registered by the conversion engine) is handled through the warning/error channel instead.

## Impact

- Primary affected code: new `src/pipeline_juridico/quality_gate.py` and new `tests/test_quality_gate.py`; no existing module is modified.
- `Phase1Artifacts` (Stage 3 output) becomes the accepted upstream input to Stage 5; Stage 3 itself is unchanged and the literal Markdown and report remain byte-identical before and after gate evaluation.
- `GateState` (already defined in `src/pipeline_juridico/contracts.py`) becomes the gate state contract; no change to its shape.
- `CriticalValidationResult` / `CriticalValidationStatus` / `CriticalFinding` (Stage 4 output) remain strictly independent; the gate never constructs, imports, or references them, and the Stage 4 module's existing independence test keeps passing.
- No new dependency, storage provider, service, database, credential, canonical bundle write, or domain-specific schema is introduced.
- Stage 6 Domain Router and later bounded-context pipelines remain out of scope and are not coupled to by this change.
