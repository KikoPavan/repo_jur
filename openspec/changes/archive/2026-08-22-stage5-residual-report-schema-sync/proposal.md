# stage5-residual-report-schema-sync

## Why

Stage 5 (Phase 1 Quality Gate) archived its residual gaps explicitly: the current Phase 1 technical report does not implement the FROZEN §6.3 minimum block layout, the FROZEN `truncamento conhecido` (known-truncation) fatal rule is not evaluable because the report contract defines no truncation signal, and the report's markdown hash covers the raw converter output instead of the boundary literal (`openspec/changes/archive/2026-08-21-stage5-phase1-quality-gate/proposal.md` Residual Risks 1–3; `openspec/specs/phase1-quality-gate/spec.md` — known-truncation deferred-evaluability statements). The Quality Gate memo itself mandates the follow-up: "A especificação operacional da Fase 1 deve ser sincronizada para: regras do gate; page inventory; JSON técnico mínimo; partial diagnostic mode; retry bounded/configurável; separação entre campos determinísticos e telemetria" (`decision-memo-phase1-quality-gate-v1.0-FROZEN.md` §14.3), and the archived gate design records that "the §14.3 report-schema synchronization must add the executable check — an explicit frozen truncation flag — before the already-normative condition becomes evaluable on the report contract; the gate would then consume it as a fatal signal without changing its architecture".

Verified against the real repository (branch `wt/r1-stage5-report-schema-sync`, HEAD `24e2e01`, 2026-08-21): `src/pipeline_juridico/models.py` `Relatorio` carries `run_id` (not `execution_id`), a flat `source` block (`path`/`size_bytes`/`sha256`/`pages` instead of `input.{sha256,byte_size,page_count}`), `output` (`path`/`sha256` instead of `artifacts.{markdown_sha256}`), no `phase1` block, no `result.{quality_gate,warnings,errors}` block, no `telemetry` block, a top-level execution `status` (`sucesso`/`incompleto`/`falha`), and per-page records `number`/`method`/`status`/`characters`/`warnings`/`error` instead of the §6.3 `page_number`/`method`/`char_count`/`warnings`/`errors` — with no truncation signal anywhere. `src/pipeline_juridico/quality_gate.py` reads the current field names through an isolated mapping (`source.sha256`, `source.pages`, `pages[].number`, `pages[].status`, `pages[].characters`, `pages[].warnings`, `pages[].error`) and implements no known-truncation check, per the recorded deferred-evaluability decision.

The FROZEN corpus mandates the target shape (`technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §6.3; `decision-memo-phase1-quality-gate-v1.0-FROZEN.md` §11.2–§11.3; `phase1-operational-spec-v1.1-FROZEN.md` §3 output 2, §6 page inventory, §7.1/§7.3 truncation as PASS/FAIL condition) and the fatal consequence of an authoritative truncation signal (`decision-memo-phase1-quality-gate-v1.0-FROZEN.md` §3.4, §8.2; `phase1-operational-spec-v1.1-FROZEN.md` §7.1/§7.3; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §8.5 `validate_no_known_truncation(report)` and §17 "known truncation causes FAIL"; `external-source-ingestion-contract-v1.6-FROZEN.md` §11 condition 4). R1 is the first item of the ordered implementation roadmap (`docs/planning/MASTER_IMPLEMENTATION_BACKLOG_stages_6_10.md` Section I item 1) because Stages 7–9 consume the report shape for provenance, index fingerprints and producer consumption.

## What Changes

- Sync the Phase 1 technical report to the FROZEN §6.3 minimum block layout: `schema_version`, `execution_id` (opaque non-empty, replacing `run_id`), `input.{sha256,byte_size,page_count}` (replacing flat `source`), `phase1.{implementation,implementation_version,logical_processing_version,relevant_config_fingerprint}` (new mandatory block), `result.{quality_gate,warnings,errors}` (serialized gate outcome, replacing the top-level execution `status`), `artifacts.{markdown_sha256}` (replacing `output.{path,sha256}`; the hash is defined over the Phase 1 literal Markdown — the boundary artifact with canonical markers and no technical method comments, per `phase1-operational-spec-v1.1-FROZEN.md` §3 output 1 and §4.2 — and over that artifact only; the CLI-written raw converter output file, which still carries marker-adjacent `<!-- método: ... -->` comments, is NOT the hashed artifact and the report does not claim to audit it — see Design Decision 6), `pages[]` records `{page_number,method,char_count,warnings,errors,truncated}` (renames plus an `errors` list replacing the single informational `error`, removal of the per-page `status` state carrier — page state becomes derivable from `method` + `errors` per op-spec §6 normalized method/state, with `truncated` as an independent fatal signal, not a state carrier — and a new mandatory per-page boolean `truncated`), and `telemetry` (an object that MAY carry non-normative per-run data — the former `runtime`, `ocr`, `timing` blocks, input/output paths, per-page durations — per memo §11.4 and the §14.3 separation of deterministic fields from telemetry).
- Add the explicit, authoritative known-truncation signal as the mandatory per-page boolean `truncated` in `pages[]`. The field is mandatory and always present on every emitted page record — absence of the field is a report-contract violation (FAIL), never equivalent to `false` and never interpreted as "no explicit knowledge". The conversion pipeline SHALL set `true` only on explicit, authoritative knowledge of output truncation for that page (no inference); when the pipeline holds no such knowledge it SHALL record `false`. This makes the already-normative fatal rule evaluable without inventing semantics, by exercising the corpus's explicit delegation of serialized field names to the operational schema (op-spec §6 "Os nomes serializados exatos podem ser definidos pelo schema operacional, mas devem permanecer engine-neutral"; memo §3.3 "Os nomes exatos podem ser normalizados pelo schema da Fase 1, desde que não dependam de um engine específico"). The full derivation chain, with verbatim corpus evidence, is in Design Decision 2; its load-bearing links: the concept "truncamento conhecido" and its fatal consequence are corpus-defined (memo §3.4, §6 c.6, §8.2; op-spec §7.1/§7.3; tech-spec §8.5 `validate_no_known_truncation(report)`, §17; ESIC §11 condition 4); the check is wired to the report by the corpus itself (tech-spec §8.5), so the report MUST carry the state; the per-page granularity is corpus-assigned (memo §8.2 under "Falha de extração"; op-spec §6 page inventory, one entry per physical page); "conhecido" (known) means explicit, authoritative knowledge — never heuristic inference (memo §8.5 prohibits implicit heuristic thresholds as fatal rules); and the §14.3 synchronization that defines the serialized form is mandated by the memo itself and was pre-determined by the human-approved Stage 5 archive ("an explicit frozen truncation flag"). Only the serialized field name (`truncated`) and type (boolean) are schema-defined — exactly the delegation op-spec §6 / memo §3.3 confer; no semantics are invented.
- Implement the executable known-truncation check in the Quality Gate: any page record whose `truncated` is `true` SHALL produce `FAIL` (`validate_no_known_truncation` becomes executable); the gate SHALL NOT infer truncation from any other observable (empty return remains its own deterministic fatal rule, char count and method only), SHALL NOT treat `truncated: false` as any signal, and SHALL treat a missing or non-boolean `pages[].truncated` as a report failure (missing required field ⇒ `FAIL`), never as equivalent to `false`.
- Update the Quality Gate's read-only field mapping to the synchronized contract: `input.sha256`, `input.page_count`, `pages[].page_number`, `pages[].method`, `pages[].char_count`, `pages[].warnings`, `pages[].errors` (the new state carrier: non-empty `errors` or `method == "erro"` ⇒ not completed, fatal), `pages[].truncated`. The gate SHALL NOT read the `result` block as an input signal and SHALL NOT read the `telemetry` block (the recorded gate result and per-run telemetry are outputs/observability, never gate inputs).
- Emit the final report in two phases so the gate stays pure and non-mutating: the conversion pipeline builds a candidate report (all deterministic blocks), evaluates the Quality Gate over the candidate artifacts, and only then emits the final report whose `result.quality_gate` is the serialized gate state and whose `result.warnings`/`result.errors` are the gate's warning/error tuples. The gate itself never mutates the report it received (the Stage 5 non-mutation invariant is preserved).
- Update the affected operational scenarios of the direct-conversion capability (`juridical-pdf-conversion`): the report outcome is the serialized gate result (`result.quality_gate`), so strict-failure and `--allow-partial` scenarios now record `FAIL` in the report (partial output never becomes `PASS`/`PASS_WITH_WARNINGS`; the affected pages remain listed).
- Migrate the report contract tests (`tests/test_report.py`), the Quality Gate tests (`tests/test_quality_gate.py`), the CLI tests (`tests/test_cli.py`) and any converter/validator consumers of the renamed per-page fields to the synchronized contract.

## Capabilities

### Modified Capabilities

- `juridical-pdf-conversion`: The report generation contract is synchronized to the FROZEN §6.3 minimum block layout (blocks `schema_version`, `execution_id`, `input`, `phase1`, `result`, `artifacts`, `pages`, `telemetry`; per-page `truncated` signal; serialized gate result recorded in the emitted report; deterministic fields separated from telemetry). The partial-mode scenarios are updated to the gate-result outcome model. No literal-Markdown behavior, OCR routing, cleaning, validation, or atomic-write rule changes.
- `phase1-quality-gate`: The gate's report field mapping follows the synchronized contract; the known-truncation fatal rule becomes evaluable through the explicit `pages[].truncated` signal; the gate records its outcome in the emitted report without mutating it; the gate never reads `result` or `telemetry` as inputs. All Stage 5 invariants (three states, determinism, non-mutation, engine-neutrality, independence from Critical-Data Validation, no routing, no production authority) are preserved.

## Non-Goals

- Inventing truncation detection heuristics: no new deterministic or heuristic truncation detector is defined by this change; the pipeline sets `truncated: true` only on explicit, authoritative knowledge (no current extractor signal produces it today — the pipeline records `false` on every emitted page record, and the check is evaluable and corpus-honest). Any heuristic truncation detector remains a future, separately-approved rule per memo §8.5.
- Adding a gate-level markdown-hash comparison: the FROZEN gate sequence (tech-spec §8.5) does not include one; this change redefines `artifacts.markdown_sha256` over the boundary literal so that any future comparison is possible, but performs none.
- Changing the direct-conversion Markdown artifact: the CLI continues to write the converter output as today (shared-conversion-core "existing direct conversion remains available without a breaking behavioral change"); only the report contract and its emission change.
- Editing any FROZEN baseline, writing to `repo_jur/bundle/`, adding or changing dependencies, modifying Stage 4 code, or implementing any Stage 6+ capability (Domain Router, Semantic Review, Producers, retrieval).
- Renaming the engine-neutral method vocabulary: the existing `texto_nativo`/`ocr_integral`/`hibrido`/`vazia`/`erro` values are retained (op-spec §3.3/§6 permit the Phase 1 schema to define the exact serialized names; they map 1:1 to the conceptual states native/OCR/hybrid/blank/error).
- Removing the converter's internal execution-status logic (`StatusExecucao` remains available internally for write/partial decisions); only the report's serialized fields change.

## Residual Risks

1. **No current extractor path populates `truncated: true`.** The field is mandatory and always emitted on every page record: absence of the field is a report-contract violation (FAIL), never equivalent to `false` and never interpreted as "no explicit knowledge". The emitted value is `false` whenever the pipeline holds no authoritative knowledge of truncation, and no current extractor path produces such knowledge — so conformant artifacts today always carry `truncated: false`. This is the corpus-honest state: the §14.3 synchronization requirement is satisfied (the signal exists, the field is mandatory, and the check is evaluable and tested), and no heuristic is invented.
2. **The gate still performs no `artifacts.markdown_sha256` comparison.** The hash is redefined over the boundary literal so the comparison is now *possible*; whether the gate should verify it is not mandated by the FROZEN gate sequence (tech-spec §8.5) and remains out of scope. The gate validates the field's presence and type only.
3. **The two-phase emission creates a candidate-report state that is not full-contract-valid** (no `result` block) between conversion and emission. This state is internal to the pipeline, never persisted, and the full report contract validation applies only to the emitted final report; the gate's input requirements deliberately exclude the `result` block (the gate derives state from structural fields).
4. **Field renames ripple through converter-internal consumers** (`validator.py` page-record mapping, converter report construction, CLI assertions). Mitigated by the task plan (explicit migration tasks) and the full-suite regression gate; no public API beyond the report contract and `Phase1Artifacts` shape changes.

## Impact

- Primary affected code: `src/pipeline_juridico/models.py` (report/per-page record reshape), `src/pipeline_juridico/report.py` (contract validation, builders, emission helper), `src/pipeline_juridico/converter.py` (report construction), `src/pipeline_juridico/conversion_engine.py` (two-phase emission at the Stage 3 boundary), `src/pipeline_juridico/cli.py` (two-phase emission at the operational surface), `src/pipeline_juridico/quality_gate.py` (field mapping + executable known-truncation check), and the affected tests (`tests/test_report.py`, `tests/test_quality_gate.py`, `tests/test_cli.py`, plus any validator/converter consumer tests).
- `Phase1Artifacts` keeps its shape (`markdown` + `report_json`); the `report_json` content follows the synchronized contract and now includes the serialized gate result.
- `GateState` and `QualityGateResult` shapes are unchanged; the gate's result semantics are unchanged.
- No new dependency, storage, service, database, credential, canonical bundle write, or domain-specific schema is introduced; no FROZEN baseline is edited.
- Downstream consumers (Stages 7–9) consume the synchronized report shape for provenance and index fingerprints, as planned by the master backlog (R1 first in the ordered roadmap).
