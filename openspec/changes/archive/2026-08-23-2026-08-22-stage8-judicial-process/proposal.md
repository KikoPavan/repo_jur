## Why

The FROZEN architecture requires the Stage 8 Judicial Process Pipeline: the `judicial_process` branch of the closed Stage 6 Domain Router, composed of the Process Semantic Review / Enrichment layer followed by the Process Producer, publishing exclusively into domain-specific process storage outside the Legal Knowledge bundle (`implementation-plan-repo-jur-v1.1-FROZEN.md` §10; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §3.4, §3.5, §17 items 26–28, §18 Stage 8; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §1.3, §1.4, §2.1A, §8.11, §11 invariants 47–52 and 66–67; `decision-memo-semantic-review-enrichment-layer-v1.1-FROZEN.md`; `decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`). Stage 6 is closed and archived: the Domain Router deterministically produces exactly one of `legal_knowledge`, `judicial_process`, `review_required` (`openspec/specs/domain-router/spec.md`; `src/pipeline_juridico/domain_router.py`), and `guard_legal_bundle_write` already reserves the Legal bundle exclusively for the `legal_knowledge` domain (`src/pipeline_juridico/contracts.py`). Stage 7 is closed and archived: the `legal_knowledge` branch (Legal Semantic Review + Legal Producer + `repo-jur producer` CLI) is implemented (`src/pipeline_juridico/legal_semantic_review.py`, `legal_producer.py`, `legal_producer_cli.py`; `openspec/specs/legal-knowledge/spec.md`) and its semantics must not be modified. No component in the current repository consumes `judicial_process`-routed artifacts: there is no Process Semantic Review, no process schema, no process-domain storage, no Process Producer, and no process write guard — the entire `judicial_process` branch is unimplemented (verified 2026-08-22 on this worktree: no `process` module, no process storage root, `bundle/` absent; the only consumer of the `judicial_process` route value is the router itself and its tests). Stage 8 must therefore create that branch: the Process Semantic Review seam, the approved process schema/profile, the process-domain storage boundary, and the Process Producer, all domain-isolated from Legal Knowledge, deterministic-where-FROZEN-demands, and bound by the immutable Phase 1 artifacts and the consumed routing decision.

The authoritative Stage 8 objective is derived directly from the FROZEN corpus: **implement the `judicial_process` branch of the Domain Router as the Judicial Process Pipeline — Process Semantic Review / Enrichment → Process Producer → process-domain storage — consuming only conformant Phase 1 artifacts explicitly routed to `judicial_process`, preserving Phase 1 immutability, keeping schemas/storage fully isolated from Legal Knowledge, and never implementing retrieval.** The FROZEN corpus defines the pipeline skeleton and all invariants; it deliberately leaves the process field inventory, enrichment schema, and storage location/format undefined ("domain-specific, governed separately" — arquitetura §1.3/§2.1A; impl plan §10/§13; shared-conversion-core memo "quando definidas"), which is an absence of authority, not a contradiction (planning backlog `docs/planning/MASTER_IMPLEMENTATION_BACKLOG_stages_6_10.md` §M.1, §M.3). Those gaps are the human-review decisions HR-3 through HR-6 below (all approved on 2026-08-23, with the HR-3 vocabulary correction and the HR-6 normative correction).

## What Changes

- Add the Stage 8 Judicial Process Pipeline as the `judicial_process` branch of the closed Stage 6 Domain Router: a Process Semantic Review / Enrichment seam followed by a Process Producer, both consuming only conformant Phase 1 artifacts (literal Markdown + technical conversion report carrying `result.quality_gate`) whose recorded gate outcome is `PASS` or `PASS_WITH_WARNINGS` and whose routing decision is exactly `judicial_process` (the existing Stage 6 `RoutingDecision` is consumed, never re-derived from document content). Unconverted input, raw PDFs, `legal_knowledge`-routed artifacts, `review_required`-routed artifacts, and gate-`FAIL` artifacts SHALL NOT enter the Stage 8 boundary (mirrors the Stage 6/7 input contracts; `phase1-operational-spec-v1.1-FROZEN.md` §14; arquitetura §1.4/§8.9; domain-router spec precedence).
- Reuse the existing shared contracts without modification: `Phase1Artifacts`, `RouteTarget`, `CriticalValidationStatus`, `GateState`, `RoutingDecision`, `guard_legal_bundle_write` (`src/pipeline_juridico/contracts.py`, `domain_router.py`), `config.py::ensure_outside_canonical_bundle`, `validator.py::write_atomic`, `hashing.py`, `report.py::validate_report_contract` — the physical-layout memo and impl plan §0/§1/§13 mandate `REUSE → ADAPT IN PLACE → TEST` and forbid parallel trees and duplication (`decision-memo-physical-layout-logical-capability-mapping-v1.0-FROZEN.md`; `implementation-plan-repo-jur-v1.1-FROZEN.md` §13).
- Create the Process Semantic Review seam: a bounded-context-specific engine whose input is the immutable Phase 1 Markdown plus the technical report, and whose output is a review result carrying structured patches (`before`/`after`/`reason`/`confidence`/`page_refs`/`evidence_refs`), extracted fields, non-authoritative classification suggestions, warnings, and the `REVIEW_REQUIRED` signal — per the FROZEN semantic-review memo (memo v1.1; tech spec §3.5). The layer SHALL NOT publish, SHALL NOT overwrite Phase 1, SHALL preserve every original word on structural operations, and SHALL be domain-isolated from Legal Knowledge (source-inspection enforced). Deterministic (non-LLM) structural review rules are versioned and registry-backed; any AI/semantic engine is adapter-based, engine-neutral, and explicitly authorized — never silent LLM classification (task invariant; tech spec §3.5, §19; arquitetura §1.4).
- Create the approved process schema/profile and the process-domain storage contract: a process frontmatter profile derived from the OKF v0.2 base rules with a process-specific type vocabulary and profile fields — never the Legal OKF Profile (`legal-okf-profile-v1.3-FROZEN.md` is Legal-only; impl plan §10 "usar Legal OKF schema como schema processual" is prohibited) — and a canonical Git-tracked process-domain storage root `<repo>/process/` separate from `repo_jur/bundle/` and from `var/`, with a dedicated process write guard defined by Stage 8 (only the Judicial Process domain writes process storage; process writes to `bundle/` are denied by the existing Legal guard, which remains unchanged and Legal-specific). Location/format/vocabulary are the HR-3/HR-4/HR-5 decisions (approved 2026-08-23); the change ships the approved contract and defers implementation of the storage adapter and Producer to a separately authorized Stage-8 implementation task.
- Create the Process Producer: the only component authorized to publish into process-domain storage. It consumes the Phase 1 artifacts (read-only) plus the review result and a validated producer context, resolves identity/provenance (PDF cardinality, sources, duplicate resolution conservatively), applies the lifecycle/ownership merge discipline (recompute Producer-Owned, preserve Human-Owned and curated Shared values, `verified`/history policy, `generated.at` meaningful-change semantics, no `_v2`), renders a process concept candidate per the approved profile, validates profile + cardinality + ownership, and publishes atomically through the process write guard — never into `repo_jur/bundle/`, never via an alternate path, never with automatic Git commit/push.
- Add a minimal operational `repo-jur process build|validate|publish` CLI surface following the Stage 7 CLI precedent and the existing conventions (argparse, environment-driven directories, sanitized logging, deterministic exit codes, atomic writes), with the existing `converter-juridico`, `repo-jur route`, and `repo-jur producer` surfaces untouched (CLI non-regression; HR-8).
- Add Process Producer observability as operational/technical artifacts only (tech spec §15.1 Producer events), stored outside `bundle/`, outside process-domain storage, and outside Phase 1 artifacts, content-safe.
- Do not implement Stage 9 (Retrieval) or any later stage; do not implement Judicial Process Retrieval, any index, chunking, or reranking; do not modify Domain Router semantics; do not modify the closed Stage 7 pipeline; do not modify FROZEN authorities.

## Capabilities

It consumes only conformant Phase 1 artifacts (gate `PASS`/`PASS_WITH_WARNINGS`, route `judicial_process`) read-only, consumes the existing routing decision without re-derivation, produces structured review patches that preserve every original word, renders process concept candidates under the approved process profile (never the Legal OKF Profile), resolves identity/provenance and duplicates conservatively, applies the lifecycle/ownership merge discipline, validates profile + cardinality, and publishes atomically into process-domain storage exclusively through the process write guard — without mutating Phase 1, without semantic content rewrite, without silent LLM classification, without Legal Knowledge behavior, without any write to `repo_jur/bundle/`, without retrieval behavior, and without automatic `verified`/`status`/versioning.

### Modified Capabilities

None.

The existing `contract-harness`, `itp-ingress-preflight-evidence`, `shared-conversion-core`, `critical-data-validation`, `phase1-quality-gate`, `domain-router`, `legal-knowledge`, and `juridical-pdf-conversion` requirements are not changed by this proposal.

## Non-Goals

- Implementing Stage 9 (Legal Knowledge Retrieval) or Stage 10 (Conformance/Regression).
- Modifying the Stage 6 Domain Router semantics, `router.py` page-level routing, the converter, OCR provider, routing thresholds, cleaner, validator, report generation, Stages 2–6 code, `contracts.py`, `config.py`, or the closed Stage 7 Legal Knowledge pipeline (`legal_semantic_review.py`, `legal_producer.py`, `legal_producer_cli.py`, `repo-jur producer` surface).
- Modifying any FROZEN authority (`docs/baselines/frozen/*`) or creating a new FROZEN memo as part of this change (the process schema/storage contract is proposed and approved through the HR decisions; if a new FROZEN memo is later desired, it is a separate human decision — HR-4/HR-5).
- Introducing semantic/LLM classification silently: any AI/semantic review engine must be explicitly authorized, adapter-based, and engine-neutral; the deterministic path is the default (HR-1/HR-2).
- Reusing the Legal OKF Profile, Legal type vocabulary, Legal schema, or Legal enrichment schema for process documents (shared-conversion-core memo *Prohibited Coupling*; impl plan §10).
- Writing process artifacts into `repo_jur/bundle/` or creating a shared Legal/Process index.
- Automatic publication authority beyond the Process Producer; any alternate write path; automatic Git commit/push/merge/archive.
- Automatic `verified` fabrication, automatic `status` mutation, `_v2`/UUID/stable-id creation.
- Implementing or validating deterministic redundant-value comparison (future capability per arquitetura §1.6).
- Adding or changing dependencies.

## Residual Risks

1. **Process schema/storage contract was not FROZEN-defined (approved human decisions).** The FROZEN corpus mandates process-owned schemas, enrichment, Producer, and storage but never defines the field inventory, ownership rules, or storage location/format (arquitetura §1.3/§2.1A; impl plan §10/§13; shared-conversion-core memo). This change therefore proposes: (a) the process type vocabulary derived from the FROZEN Stage 8 scope (impl plan §10 — petições, contestações, decisões, procurações, testamentos, anexos, demais peças), approved exactly as `Peticao | Contestacao | Decisao | Procuracao | Testamento | Anexo | OutraPeca` (HR-3); (b) the approved process-domain storage root (`<repo>/process/`, canonical Git-tracked process storage outside `bundle/` and outside `var/`, arquitetura §11.50 classifies canonical/domain storage as Git-tracked — HR-4); and (c) the approved frontmatter profile (OKF v0.2 base rules + process profile, never the Legal profile — HR-5). All three are approved human decisions (HR-3/HR-4/HR-5, recorded 2026-08-23) and the storage adapter + Producer implementation tasks remain gated on a separately authorized Stage-8 implementation task; no agent resolves them silently (master backlog §M.1).
2. **Process-domain lifecycle/ownership/duplicate/verification rules are stated explicitly in the Stage-8 OpenSpec (HR-6).** The Legal-bundle-scoped memos (`lifecycle-field-ownership-v1.4`, `decision-memo-duplicate-act-handling-v1.0`, `decision-memo-verification-history-schema-v1.0`, and `legal-okf-profile-v1.3`) govern `/bundle/` concepts and do NOT become normative authorities for Judicial Process by analogy (HR-6 normative correction). Stage 8 reuses only the conservative mechanics proven in Stage 7 and states the process-domain lifecycle, ownership, duplicate and verification requirements explicitly and self-sufficiently in the `judicial-process` spec: deterministic recompute of Producer-Owned, preservation of Human-Owned and curated Shared, no fabricated `verified`, no `_v2`, conservative duplicate resolution blocked on ambiguity/material uncertainty, and no content-based safe-equivalence in v1.
3. **The process `type` authority is not FROZEN-defined.** No baseline says how a `judicial_process`-routed artifact is typed (petição vs decisão vs testamento...). Stage 6 explicitly denied content-derived routing signals (HR-1, archived), and Stage 7 approved explicit operator intent for the Legal `type`. This change mirrors that: explicit operator intent in the validated producer context is the deterministic source (HR-3), with any semantic classification suggestion non-authoritative and conflicting suggestions routed to `REVIEW_REQUIRED`.
4. **The Critical-Data Validation status is not recorded in the Phase 1 report.** Stage 8 inherits the Stage 6/7 input shape: the boundary is reached only after the router emitted `judicial_process`, which itself required gate `PASS`/`PASS_WITH_WARNINGS` and critical status `OK`/`WARNING` (domain-router spec precedence). Stage 8 re-reads the recorded gate outcome from the report (structural enforcement) and does not depend on a non-existent critical-status field.
5. **`sources[].resource` provenance threading is not FROZEN-defined for process concepts.** Same gap as Stage 7 (HR-4 there): the Phase 1 technical report carries `input.sha256` + `execution_id` but not the preserved-evidence resource URI (the ingress state record does). The Process Producer receives the preserved-evidence reference through the validated producer context, cross-checked against `input.sha256` when resolvable, never invented (HR-7).
6. **Process duplicate resolution is a process-domain requirement, not a Legal memo extension.** `decision-memo-duplicate-act-handling-v1.0` is written for Legal acts/concepts and is not a normative authority for process storage (HR-6 normative correction). The conservative resolution state machine (physical identity → logical resolution → NO-OP/controlled update/distinct concept/HUMAN REVIEW) is stated explicitly as a process-domain requirement in the `judicial-process` spec, with writes blocked on ambiguity/material uncertainty and no content-based safe-equivalence in v1 (HR-6). A future process-specific duplicate memo may refine this; it is deferred.
7. **Enrichment field inventory is empty by default.** Consistent with the semantic-review memo (which authorizes the layer and its invariants, not a specific field set) and with the Stage 7 precedent (empty-by-default rule registry), v1 ships the deterministic structural patch framework with an empty rule registry and no process enrichment field inventory; specific enrichment fields become a future change now that the profile is approved (HR-5, recorded 2026-08-23). No normative rule is invented without a FROZEN citation or approved human decision.

## Human Review Decisions (Approved 2026-08-23)

- **HR-1 — Deterministic-first scope for the Process Semantic Review seam**: APPROVED — Stage 8 v1 ships the Process Semantic Review as a deterministic, rule-registry-backed seam; the AI/LLM engine is deferred to a future authorized change (mirroring the approved Stage 7 HR-1) — see design Decision 4.
- **HR-2 — No LLM engine in Stage 8 v1**: APPROVED — no model/provider/prompt for a semantic/LLM review engine is selected or invoked in this change; the seam stays engine-neutral and the deterministic path is default; any future LLM engine requires a separately authorized change (design doc §20.5 out-of-scope preserved; mirroring the approved Stage 7 HR-2) — see design Decision 4.
- **HR-3 — Process document type authority and vocabulary**: APPROVED — the deterministic source of the process concept `type` is the explicit validated operator intent carried in the validated producer context; the approved vocabulary is exactly `Peticao | Contestacao | Decisao | Procuracao | Testamento | Anexo | OutraPeca`; any semantic classification suggestion is non-authoritative and a suggestion conflicting with the explicit `type` routes to `REVIEW_REQUIRED`; no content-derived `type` — see design Decision 5.
- **HR-4 — Process-domain storage contract**: APPROVED — the canonical process-domain storage root is `<repo>/process/` (Git-tracked, outside `repo_jur/bundle/` and outside `var/`, never sharing the Legal bundle tree), with positional concept paths, atomic publication, and a dedicated process write guard defined by Stage 8 (only `judicial_process` may write process storage; no alternate publication path). The existing `guard_legal_bundle_write` remains unchanged and Legal-specific; process writes to `bundle/` are denied by its existing semantics. This resolves the mandatory human decision M.1 of the planning backlog — see design Decision 6.
- **HR-5 — Process frontmatter profile**: APPROVED — process concept candidates follow the OKF v0.2 base concept rules with a process-specific profile (never the Legal OKF Profile fields, Legal type vocabulary, or Legal schema), including `status` Human-Owned, `verified` never fabricated, `generated.at` meaningful-change semantics, and no `_v2`/UUID/stable-id — see design Decision 7.
- **HR-6 — Lifecycle/ownership/duplicate/verification governance**: APPROVED WITH NORMATIVE CORRECTION — Stage 8 may reuse the conservative mechanics proven in Stage 7, but the Legal-scoped FROZEN memos do NOT become normative authorities for Judicial Process by analogy; the judicial-process OpenSpec states the process-domain lifecycle, ownership, duplicate and verification requirements explicitly and self-sufficiently, preserving deterministic Producer-Owned recomputation, Human-Owned preservation, curated Shared preservation, verification-history discipline, conservative duplicate handling, write blocking on ambiguity/material uncertainty, and no content-based safe-equivalence in v1 — see design Decision 8.
- **HR-7 — Preserved-evidence reference threading**: APPROVED — the `sources[].resource` for PDF-derived process concepts is supplied through the validated producer context (the preserved evidence reference), matched against `input.sha256` from the report, and never invented; a missing evidence reference for PDF-derived content is a configuration error (mirroring the approved Stage 7 HR-4) — see design Decision 9.
- **HR-8 — Operational process CLI surface and write semantics**: APPROVED — the `repo-jur process build|validate|publish` surface (distinct from the Legal `repo-jur producer` group); `build`/`validate` never write to process-domain storage or the bundle; `publish` is the single write path through the process write guard; no automatic Git commit/push is introduced (mirroring the approved Stage 7 HR-6) — see design Decision 10.
