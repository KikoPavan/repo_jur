## Context

Stage 7 (`legal_producer.py`, `legal_producer_cli.py`, `legal_semantic_review.py`) was designed and validated end-to-end against single-unit real-corpus documents (`L10.406_CC_2002.pdf`, `AIRESP-1833684-2020-02-12.pdf`). The 1:1 assumption is baked into the data model itself, not just the CLI:

- `Phase1Artifacts(markdown, report_json)` — one Markdown string, one report, no notion of sub-ranges.
- `ProducerContext(type, evidence_resource)` — one type for the whole call.
- `_base_candidate()` always does `body=artifacts.markdown` (verbatim, whole-document).
- `resolve_concept_path()` derives one path per call.
- `producer_cli.py::_run_build` emits exactly one `candidate` in its JSON payload; `_run_publish` targets exactly one file.

Real STJ/CNJ bulletins ("Jurisprudência em Teses", "Precedentes Qualificados", and likely future compilations) are **structurally multi-unit inside one PDF**: distinct edições/temas/precedentes, each with a title, a date or status line, and its own page range, concatenated in one file by the publishing court. Nothing in Phase 1 (conversion) is wrong — the literal Markdown correctly represents the PDF's content and page markers. The defect is that Stage 7 has no seam to recognize "this Markdown is actually N units" before it renders a candidate.

## Goals / Non-Goals

**Goals**
- Add exactly one new architectural seam: deterministic **segmentation** of Phase 1 Markdown into 0..N ordered, page-bounded segments, based only on structural/typographic signals versioned in a rule registry — never content classification, never LLM.
- Preserve the mono-concept path exactly as-is when no unambiguous boundary exists (`SINGLE`), so `AIRESP-1833684-2020-02-12` and `L10.406_CC_2002` keep working without any observable behavior change.
- Give the operator full visibility and control: inspect segment count/boundaries/pages before building anything (`analyze`), build one or all segments explicitly, and publish each concept independently — never a bulk "publish everything" shortcut.
- Fail closed on ambiguity: a document that shows partial/inconsistent structural signal is blocked for human decision, never silently split and never silently collapsed to one giant candidate.
- Keep segment identity honest: a segment's `TemaJuridico`/`PrecedenteVinculante`/etc. identity is derived only from that segment's own canonical fields (unchanged `_deterministic_extract`/`validate_candidate` rules, now scoped per-segment body) — an "Edição N" boundary label is never smuggled in as `repo_jur_tema_numero`.

**Non-Goals**
- Not inferring `type` from content — the operator still supplies exactly one `--type` for the whole `build`/`analyze` invocation; a source with N segments assumes all N segments share the same operator-declared type (an operator publishing mixed-type units from one PDF runs the CLI per type-appropriate segment selection; this is a CLI/operator workflow concern, not a segmentation concern).
- Not building a generic ML/heuristic "detect any document layout" system — the registry only recognizes rules explicitly authored and evidenced against known corpus structures; unrecognized structures stay `SINGLE` (safe default) or `AMBIGUOUS` (fail closed), never silently split.
- Not extending the OKF Legal Profile with new fields (e.g. "edição") in this change — see proposal.md Out of Scope. If the "Jurisprudência em Teses" corpus turns out to need a field the current profile doesn't have, that is reported as a finding, not patched here.
- Not changing Stage 9 retrieval's indexing/chunking behavior — it already treats each published `.md` file under `bundle/` as an independent `concept_id`; multiple concepts sharing one `repo_jur_pdf_hash` is already legal per the existing multi-source/plural-hash contract, and per-concept indexing requires no code change once N concepts are actually published as N files.

## Decisions

### Decision 1 — Segmentation is a new, separate, upstream module — not inside Producer or Review
- **What:** Create `legal_source_segmentation.py` exposing:
  ```python
  class SegmentationOutcome(str, Enum):
      SINGLE = "single"
      SEGMENTS = "segments"
      AMBIGUOUS = "ambiguous"

  @dataclass(frozen=True)
  class Segment:
      segment_id: str          # deterministic, position-derived (e.g. "segment-0001"); NOT a legal identifier
      source_unit_label: str   # verbatim boundary heading line, unmodified; structural/operational metadata only,
                                # never written into canonical frontmatter and never used as a path/identity fallback
      body: str                # contiguous literal slice of the source markdown,
                                # including its own [[Pág. N]] markers
      page_start: int
      page_end: int
      boundary_rule_id: str | None   # None for the single implicit segment

  @dataclass(frozen=True)
  class SegmentationResult:
      outcome: SegmentationOutcome
      segments: tuple[Segment, ...]     # exactly one Segment when SINGLE; empty when AMBIGUOUS
      ambiguity_reason: str | None      # populated only when AMBIGUOUS

  def segment_markdown(markdown: str, registry: SegmentationRuleRegistry) -> SegmentationResult: ...
  ```
  `segment_markdown` is a pure function: same input Markdown + same registry version → same output, always. It never receives `ProducerContext`, `type`, or the technical report — segmentation is blind to operator intent and to Quality Gate outcome (those remain the Producer's/CLI's job to check before or after, exactly as today).
- **Why:** The task requires distinguishing "source document" vs "segment/unit" vs "published concept" (Principle 5). A new module is the only option that does not (a) push type-awareness into the type-blind Legal Semantic Review (forbidden, and exactly the anti-pattern the prior `fix-legal-review-false-block` change removed), or (b) bloat the Producer with content-boundary logic mixed into candidate rendering/validation. It also gives the smallest possible diff surface and the cleanest test seam: segmentation can be fully unit-tested on raw Markdown strings with zero producer/report/context scaffolding.
- **Alternatives considered:**
  - *Segmenting inside `legal_semantic_review.py`* — rejected: violates the closed `legal-knowledge` requirement that Review stay engine-neutral/bounded-context and not encode structural assumptions specific to bulletin-shaped sources; also Review's `ReviewResult` has no place to carry N sub-bodies.
  - *Segmenting inside Phase 1 (conversion)* — rejected: Phase 1 artifacts (`output/*.md`, `logs/*.report.json`) are contractually immutable and produced by a closed, separately-versioned pipeline stage (Stages 1-5); segmentation is Stage 7-specific business logic (which types can even span segments, which registry rules apply) and must not leak upstream.
  - *Segmenting inside the Producer CLI only (`legal_producer_cli.py`)* — rejected: would make segmentation untestable independent of state-dir/report/context plumbing, and would prevent `analyze` from being a pure read-only preview; also violates "smallest correct extension" by conflating boundary detection with candidate rendering/validation/publication concerns already owned by `legal_producer.py`.

### Decision 2 — Boundary rules are a versioned registry, structurally anchored, corpus-evidenced
- **What:** `SegmentationRuleRegistry` mirrors the existing `LegalReviewRule` provenance discipline (`rule_id`, `rule_version`, `scope`, `source`, `validation_logic_version`, plus a `detect(markdown) -> list[BoundaryMatch]` callable). Two rules ship pre-registered for the CLI's default registry:
  1. `jurisprudencia-em-teses-edicao-v1` — matches lines of the exact shape `Edição n. NNN Brasília, D de MÊS de AAAA` (day/month/year all present, "Brasília" literal, at the start of a physical line). This line occurs **exactly once per edição**, immediately preceding that edição's own all-caps running header (`EDIÇÃO N. NNN: <TITLE>`), which itself repeats on every subsequent page of the same edição as a page header — the rule anchors on the date-bearing line specifically because it is not repeated, unlike the running header.
  2. `precedentes-qualificados-tema-repetitivo-v1` — matches lines of the exact shape `Tema Repetitivo NNN  Situação <status>  Órgão <colegiado>` (fixed three-field tabular record header). Internal cross-references like `Tema em IRDR n. 11/TJSP` or a bare `Tema 692` prose mention do not match this three-field shape and correctly produce no boundary.
  A rule that matches 0 times → no contribution (stays `SINGLE` if no other rule matches either). A rule that matches ≥2 times with **consistent** spacing/shape → `SEGMENTS`, one segment per match, sliced from that match's start to the next match's start (or EOF for the last). A rule that matches ≥2 times but with **inconsistent** capture (e.g. one match is missing the date group that the pattern's own capturing group requires) is treated by the pattern simply not matching that occurrence — the design does not need a separate "partial match" state per rule; genuine ambiguity arises at Decision-3's cross-rule/overlap check, not from partial regex captures.
- **Why:** Provenance/versioning discipline mirrors already-accepted patterns in this repo (`LegalReviewRule`) so reviewers already know how to audit it. Anchoring on the least-repeated, most specific line (the dated line, or the fixed tabular header) — rather than the frequently-repeated running header or a bare number citation — is what makes the two shipped rules unambiguous by construction and testable against the real corpus lines already observed in `output/Jurisprudencia_Teses_D.P.C._ed.171.md` and `output/STJ - Precedentes Qualificados.md`.
- **Alternatives considered:** Anchoring on the repeating running header (`EDIÇÃO N. NNN: ...`) directly — rejected, because the same header string repeats on every page of that edição, making "boundary" vs. "continuation" ambiguous without extra state; the dated line is a strictly better anchor because Phase 1 emits it exactly once per unit in this corpus. Anchoring on `Tema n. NNN` bare citations — rejected explicitly per the task's Principle 4 (never use a bare internal citation as identity/boundary).

### Decision 2bis — Real-corpus evidence update: the fixed tabular record header uses a private-use Unicode glyph between the record number and the first field label, not two literal spaces there

**What actually happened:** orchestrator validation against the real Phase 1 artifact `output/STJ - Precedentes Qualificados.md` (produced by the unmodified, already-closed Stage 1-5 pipeline; not touched by this change) found that `precedentes-qualificados-tema-repetitivo-v1`, as specified in Decision 2 with a two-literal-space (`{2}`) separator between *every* field, matches **zero** times against the real document. Precise, position-verified byte-level inspection (`re.finditer` over the real file, not a synthetic fixture, cross-checked a second time after an implementer caught an imprecision in the orchestrator's first transcription) of all 10 real header lines shows exactly:

```
Tema Repetitivo 692 \uE205 Situação Trânsito em Órgão PRIMEIRA SEÇÃO
Tema Repetitivo 731 \uE205 Situação Acórdão Órgão PRIMEIRA SEÇÃO
... (10 occurrences total, one per Tema Repetitivo record)
```

Precisely, per real occurrence: the separator between the record number (`NNN`) and the fixed label `Situação` is the exact 3-character sequence **space + U+E205 (Unicode Private Use Area) + space** (` \uE205 `) — a single private-use code point flanked by one ASCII space on each side, never two consecutive occurrences of it and never U+E205 anywhere else in the line. The separator between the status value and the fixed label `Órgão` is an ordinary **single ASCII space**, exactly as in normal prose — **not** two spaces and **not** U+E205. This is a corpus-evidenced, asymmetric separator shape: only the number→`Situação` boundary carries the private-use glyph; the status→`Órgão` boundary does not.

This is the same class of finding as already-documented, already-accepted evidence in this repo (e.g. `fix-html-thin-space-normalization`'s `&#8201;` finding): Phase 1's literal, byte-faithful transcription surfaces an engine-specific character that the original rule specification assumed away without checking the real file. Decision 2's original regex (`{2}` two literal spaces at both field boundaries) was written against an *assumed* rendering of the header, not the real artifact; this is registered here as the authoritative, position-verified correction before any code changes, per project OpenSpec discipline (evidence precedes implementation).

**Correction adopted (structural, not cosmetic):**
- The rule's structural anchor is unchanged in kind — a fixed three-field tabular record header `Tema Repetitivo NNN <SEP1> Situação <status> <SEP2> Órgão <colegiado>` on its own physical line — but the two field-boundary separators are no longer required to be identical, and are each explicitly and independently one of the corpus-evidenced literal forms actually observed:
  - `<SEP1>` (between the record number and `Situação`): exactly two ASCII spaces (the originally specified, still-valid equivalent form used by the `Jurisprudência em Teses` corpus's own possible future variants) **or** exactly the 3-character sequence space + U+E205 + space (the real `Precedentes Qualificados` corpus's actual separator).
  - `<SEP2>` (between the status value and `Órgão`): exactly two ASCII spaces (originally specified) **or** exactly one ASCII space (the real corpus's actual separator at this boundary).
  No other separator width/character is accepted at either boundary; a single ASCII space at `<SEP1>`, three-or-more spaces, a bare U+E205 with no flanking spaces, or U+E205 at `<SEP2>` do **not** match. This is not a whitespace-normalization change and does **not** touch `re.sub`/normalization of the Phase 1 Markdown itself (Phase 1 remains byte-for-byte immutable; only the *detection regex*'s accepted-literal-forms set changes, never the source text).
- U+E205 is recognized **only** inside this specific structural anchor, only at the `<SEP1>` position, and only in its exact flanked form (space + U+E205 + space). It is not globally substituted, stripped, or normalized anywhere in the pipeline, and no other rule or module gains U+E205 awareness. A bare `Tema Repetitivo N` citation elsewhere in running prose — with or without a stray U+E205 nearby, and regardless of spacing — still does not match this anchor unless the complete three-field shape (number + both correctly-shaped separators + both fixed labels `Situação`/`Órgão`) is present on one physical line.
- `repo_jur_precedente_numero` continues to be resolved only from the segment's own header occurrence(s); an internal citation to a different Tema Repetitivo number inside the segment body still never overrides or contributes to that resolution (Decision 5/6 unchanged).
- Fail-closed behavior (Decision 3) is unchanged: a header line missing either required separator in its correct form/position, missing a fixed label, or otherwise incomplete does not match any accepted form and is correctly treated as "no boundary here" (or, if it partially matches in a way that produces zero-content segments or conflicting rule activations, routes to `AMBIGUOUS` exactly as already specified).

**Why not a broader fix:** A generic `\s+`/`.*` separator at either boundary would satisfy this one corpus file but would also make the rule match accidental whitespace-only look-alikes inside unrelated running prose, reopening exactly the "bare citation as boundary" failure mode the task's Principle 4 (and Decision 2's original rationale) forbids. Enumerating the specific, corpus-evidenced separator forms at each boundary independently keeps the rule exactly as unambiguous-by-construction as originally designed, while now actually matching the real artifact it was written for.

**Alternatives considered:**
- Normalizing U+E205 to two ASCII spaces in Phase 1 or in a pre-processing step before segmentation — rejected: violates the immutability guarantee for Phase 1 Markdown and the explicit instruction that no global character substitution occurs; segmentation must detect the source's real byte content, not a normalized copy of it.
- Loosening either separator to `\s*`/`.*` unrestricted — rejected: reintroduces exactly the "any separator, any content" ambiguity Decision 2 was designed to avoid; would risk matching accidental whitespace sequences inside body prose that happen to contain the words "Situação"/"Órgão" outside a genuine tabular record.
- Requiring the same separator form at both boundaries (symmetric assumption) — rejected after position-verified re-inspection: the real corpus is asymmetric (U+E205-flanked at the first boundary, plain single space at the second); forcing symmetry would either miss the real corpus (if U+E205 required at both) or over-accept a single space at the first boundary too (reopening ambiguity risk against running prose, which commonly has single-space "Tema Repetitivo NNN Situação..." as an artifact of paragraph wrapping in unrelated contexts — never actually observed in this corpus, but not ruled out generically).

### Decision 3 — Ambiguity detection: cross-rule conflicts and structural sanity checks fail closed
- **What:** Before accepting a `SEGMENTS` outcome, the registry runner performs two sanity checks: (a) no two different registered rules both produce ≥1 match in the same document (a document matching two unrelated bulletin shapes cannot be confidently segmented by either); (b) matches must be monotonically increasing in page order and each resulting segment must contain at least one `[[Pág. N]]` marker (a "boundary" with zero content pages, e.g. two adjacent header lines with no body between them, indicates a numbering/format anomaly, not a genuine unit). Either check failing routes to `AMBIGUOUS` with a specific `ambiguity_reason` string (e.g. `"conflicting_boundary_rules"`, `"empty_segment_body"`), never a partial/best-effort split.
- **Why:** Matches Principle 8 (fail-closed on ambiguity) and Principle 9-adjacent "no silent split" instruction literally: the system must be able to explain *why* it refused to segment, in the operator-visible `analyze`/`build` output, not just return a boolean.
- **Alternatives considered:** Best-effort split with a warning — rejected per explicit user instruction ("ambiguidade não pode gerar divisão silenciosa"); a warning is not a block, and the task requires blocking.

### Decision 4 — CLI surface: `analyze`, `--segment`, `--all-segments`, unchanged default
- **What:**
  - `repo-jur producer analyze <markdown> <report> --type TIPO` — read-only. `--type` is now **required** for `analyze` (not optional), because `identity_status` cannot be computed without knowing which profile's fields apply. Runs `segment_markdown()` and, per segment, computes `resolve_segment_identity(type, segment.body)`; prints outcome, segment count, and per-segment:
    `{segment_id, source_unit_label, page_start, page_end, boundary_rule_id, identity_status, identity_fields, identity_reason}`
    where `identity_status` is exactly one of `resolved` / `requires_operator_metadata` / `ambiguous` (Decision 5), `identity_fields` contains only canonical fields actually and unambiguously extracted from that segment's own body, and `identity_reason` is populated whenever `identity_status` is not `resolved`. This is a diagnostic/preview report only — it never writes to `state-dir` or `bundle/`, and no field it reports is itself a publication.
  - `producer build ... [--segment SEGMENT_ID | --all-segments]` — segment selection is by `segment_id` (not a bare ordinal, to keep the identifier stable and self-describing, e.g. `segment-0001`), matching `analyze`'s reported ids. Before rendering, `build` computes the same `resolve_segment_identity()` for the targeted segment(s): only a segment whose `identity_status` is `resolved` produces a candidate; a segment whose status is `requires_operator_metadata` or `ambiguous` blocks that segment with `LegalProducerBlockedError(reason="identity_unresolved")` and does **not** fall back to any filename/evidence-slug/editorial-label path. `--all-segments` builds every segment independently — segments with resolved identity produce candidates, segments without are reported as blocked in the same response (`candidates: [...]` plus `blocked_segments: [...]`), so the operator can still see and act on the full picture in one call. Supplying neither `--segment` nor `--all-segments` against a `SEGMENTS` outcome is `EXIT_BLOCKED` with reason `segmentation_multi_concept`; supplying either against a `SINGLE` outcome is a `LegalProducerConfigurationError` (`EXIT_CONFIG`) — nonsensical combination, fails loud not silent.
  - `producer publish` is unchanged in shape (it already takes one `--candidate` file); publishing N segments means running `publish` N times, once per candidate file the operator chose to write out from `build --all-segments`/`--segment`. This preserves "operator can publish each concept separately" (task requirement) with zero new publish-side logic.
- **Why:** Smallest CLI diff that satisfies every operator capability listed in the task (analyze, view segment count/reason, inspect page ranges, validate each candidate, publish each concept separately, block/publish selectively) without a breaking change to any existing flag, exit code, or JSON key for the `SINGLE` (today's only real) case.
- **Alternatives considered:** Auto-detecting and silently building/publishing all segments — explicitly forbidden (Principle 8, "não publicar uma coleção inteira como um único conceito apenas porque o build tecnicamente consegue renderizá-la" — the inverse failure mode, publishing all as many, is equally forbidden without explicit operator action per segment/flag).

### Decision 5 — Three explicit tiers: source document, source segment, legal concept; identity is never inferred from the segment label

A **structural boundary** is not a **legal identity**. This change formalizes three distinct entities and forbids conflating them:

1. **Source document** — the whole Phase 1 artifact (`Phase1Artifacts`: full Markdown + report), identified by `repo_jur_pdf_hash`/evidence resource. Unchanged by this proposal.
2. **Source segment** — a structural unit found by `segment_markdown()`: a contiguous, page-bounded slice of the source document's Markdown, identified only by:
   - `segment_id` — a deterministic, position-derived identifier (`f"segment-{ordinal:04d}"`, stable given the same registry version and Markdown; **not** a legal identifier and never rendered into canonical frontmatter),
   - `source_unit_label` — the verbatim boundary heading text (e.g. `"Edição n. 171 Brasília, 4 de junho de 2021"`, or `"Tema Repetitivo 692"`), kept strictly as descriptive/operational metadata,
   - `page_start`/`page_end`, and `boundary_rule_id`.
   A segment is a purely structural/operational fact. It carries no legal authority and is never itself published.
3. **Legal concept** — the `ConceptCandidate` the Producer may render and publish from a segment's body, whose identity MUST be resolved according to the OKF Legal Profile rules for the operator-declared `type`, from that segment's own body content, exactly like whole-document identity resolution today.

**`segment.source_unit_label` (or any other structural/editorial label) SHALL NEVER be used, directly or as a "last-resort" fallback, to populate a canonical domain-specific identity field (`repo_jur_tema_numero`, `repo_jur_precedente_numero`, `repo_jur_processo_numero`, etc.) and SHALL NEVER be used as a filename/path fallback that stands in for an unresolved legal identity.** The previously proposed "slug fallback from segment title when canonical fields are absent" is **removed**. Concretely:

- `resolve_concept_path()` keeps its existing whole-document fallback behavior (`_slug(evidence_resource, report)`) **only** for the `single`-outcome, whole-document case, exactly as today — this preserves the existing acceptance contract for documents that legitimately have no canonical number (e.g. doctrinal `TemaJuridico`) and were already accepted under today's rules.
- For a segment-derived candidate (`segments` outcome), if the segment's own body does not yield the canonical identity fields the `type` requires (conditionally or unconditionally) for a real, distinct concept, the Producer **does not render a publishable candidate** at all. `_base_candidate()`/`produce()`/`build` compute an `IdentityResolution` for the segment (see below) *before* attempting to build; a segment whose identity is not resolved raises `LegalProducerBlockedError(reason="identity_unresolved")` — it does not fall through to a filename/evidence-slug/editorial-title path.

**`IdentityResolution`** (new, small, pure function `resolve_segment_identity(concept_type, segment_body) -> IdentityResolution`, reusing the existing per-type deterministic extraction, unchanged):
```python
class IdentityStatus(str, Enum):
    RESOLVED = "resolved"                        # canonical identity fields for this type are present and unambiguous
    REQUIRES_OPERATOR_METADATA = "requires_operator_metadata"  # type allows conditional fields; none found, and the type's profile has no doctrinal/abstract fallback that is safe for a *segment* (see Decision 6)
    AMBIGUOUS = "ambiguous"                        # candidate identity fields conflict or cannot be disambiguated from the segment body alone

@dataclass(frozen=True)
class IdentityResolution:
    status: IdentityStatus
    fields: Mapping[str, object]   # canonical fields actually extracted from the segment body, empty if unresolved
    reason: str | None             # populated when status is not RESOLVED
```
- **Why:** This is the direct fix requested: "a fronteira estrutural e a identidade jurídica do conceito são coisas diferentes." Treating `segment_id`/`source_unit_label` as pure structural/operational metadata (never legal identity, never a path-fallback source) makes the distinction impossible to blur by construction, and it makes `analyze`'s `identity_status` field meaningful and auditable per segment.
- **Alternatives considered:** Keeping the title-as-slug fallback "just for segments" — rejected: this is exactly the masking behavior forbidden by the user (publishing under a filename that looks legitimate while carrying no real legal identity is worse than a mono-document doctrinal fallback, because a segment fallback would make N differently-numbered files that all *look* like distinct legal concepts without being backed by resolved identity).

### Decision 6 — Explicit finding: "Jurisprudência em Teses" edições are NOT valid `TemaJuridico` concepts under the current OKF profile

Analysis of the real corpus (`output/Jurisprudencia_Teses_D.P.C._ed.171.md`) against the current, closed `legal-knowledge` spec's `TemaJuridico` profile:

- `repo_jur_tema_numero` is documented as "Mandatory if representing **an official numbered theme**" — i.e., one specific `Tema Repetitivo`/`Tema de Repercussão Geral` decided by the court under one official number. Each "Edição N" of the STJ's "Jurisprudência em Teses" bulletin is an **editorial compilation of multiple independent theses** on a subject (e.g. "Edição 171: Dos Embargos de Divergência - II" bundles several distinct holdings, each of which may itself cite several different, unrelated `Tema n. N` numbers as grounding — as the corpus shows: 0, 1, or many distinct `Tema n. N` citations per edição, none of which is "the" edição's own official number). An "Edição" number is a **publisher/bulletin-issue identifier**, not a court's official theme number; conflating the two would misrepresent the legal nature of the concept.
- The profile's existing "doctrinal/abstract `TemaJuridico`" allowance (both `repo_jur_tema_numero` and `repo_jur_tribunal` conditionally absent) exists for a genuinely abstract/doctrinal theme document — not for a bulletin that aggregates dozens of unrelated official themes under one editorial issue number. Publishing an "Edição" under that allowance, identified only by a positional/slug fallback, would produce a `TemaJuridico` concept with no real thematic identity at all — exactly the outcome Decision 5 forbids.
- **Conclusion: under the current OKF Legal Profile, individual "Edições" of "Jurisprudência em Teses" are NOT sound `TemaJuridico` concepts**, and this change does **not** attempt to force that fit. `producer build --type TemaJuridico` against a segment of this corpus resolves `IdentityStatus.REQUIRES_OPERATOR_METADATA` (no canonical identity in the segment body; the doctrinal-absence allowance does not apply because the segment is demonstrably a multi-theme editorial compilation, not a single doctrinal theme) and **blocks fail-closed** with reason `identity_unresolved`, together with a message explaining the mismatch (`"jurisprudencia_em_teses_edicao_not_valid_temajuridico"` or equivalent).
- **If** the business later decides this document class should be formally supported, the correct minimal extension — **out of scope for this change**, requiring its own separately authorized OpenSpec change — would add a distinct editorial-collection identity field to the profile (e.g. `repo_jur_edicao_numero` + `repo_jur_edicao_titulo`, under a new or extended concept type, not reusing `repo_jur_tema_numero`) with its own path scheme (e.g. `boletins/jurisprudencia_em_teses/edicao_171`). This change documents the finding and the shape of that future extension but does not implement it.
- **PrecedenteVinculante contrast:** `Tema Repetitivo N` in "STJ - Precedentes Qualificados.md" **is** the court's own official repetitive-theme number for that segment (the segment's fixed tabular header itself *is* the record's canonical identity field, not an editorial label), so `repo_jur_precedente_numero`/`repo_jur_tribunal` resolve directly and unambiguously from the segment body — `IdentityStatus.RESOLVED` — with zero extension needed. An internal cross-reference inside a segment (e.g. `Tema em IRDR n. 11/TJSP` mentioned inside the Tema 1016 segment) never overrides or contributes to that segment's own resolved identity.

> **Correction (Decision 11):** the contrast above is imprecise for `repo_jur_tribunal`. The fixed `Tema Repetitivo` header supplies the own precedent number and status only; it does not, by itself, imply STJ or any other tribunal. Tribunal identity requires separate own textual evidence under Decision 11. The original text is retained here as historical context, but this correction is authoritative.

### Decision 7 — Real-corpus finding: page context is a positional property of the whole document, not a per-segment content check (post-1bis finding, same change)

**What actually happened:** orchestrator validation of the corrected `precedentes-qualificados-tema-repetitivo-v1` rule (Decision 2bis) against the real `output/STJ - Precedentes Qualificados.md` file found a second, independent defect in Decision 3(b)'s original page-range mechanism, not in the boundary regex itself. `_page_range()` (as implemented in Task 1.3/1bis.3) derived `page_start`/`page_end` only from `[[Pág. N]]` markers found strictly *inside* each segment's own sliced body — never from the document's page-marker positions outside that slice. Position-verified inspection of the real file shows this produces a wrong page attribution whenever a physical page hosts two or more `Tema Repetitivo` records: the STJ places the `[[Pág. N]]` marker once, at the page's own start, and then several records that structurally begin on that same physical page follow inside the same page's Markdown span before the *next* page marker appears. Concretely: `Tema Repetitivo 978`'s header appears strictly after the `[[Pág. 4]]` marker and strictly before the `[[Pág. 5]]` marker (its own body slice legitimately contains no marker at all — correctly `page_start=page_end=4`), but `Tema Repetitivo 999`'s header also appears after `[[Pág. 4]]` and before `[[Pág. 5]]` — its own sliced body, however, *does* happen to contain the `[[Pág. 5]]` marker (because its content continues onto page 5) — and the old per-segment-substring `_page_range()` used only that contained marker, reporting `page_start=page_end=5` for a record whose header, and therefore whose `Tema Repetitivo` identity, factually starts on page 4. This is a real 1:N page-attribution defect: two structurally distinct records legitimately sharing one physical page must both be able to report that shared page as their `page_start`, and neither a segment's own absence of a marker, nor a marker that happens to fall inside its body slice for an unrelated reason (continuation onto the next page), may be used as the sole page-resolution signal.

**Correction adopted (structural, not cosmetic):** page resolution is redefined as a pure positional query against one document-wide marker map, computed once per `segment_markdown()` call, never per-segment:

1. Build `page_map: list[tuple[offset, page_number]]` by a single `finditer` pass over the *whole* input Markdown for `[[Pág. N]]`, in document order. This is the same regex already used for `_page_range()`; only its scope changes (whole document, once, not per-segment-slice, per-call).
2. Validate the map once: offsets must be strictly increasing (a `finditer` invariant, not itself a new check) **and** page numbers must be non-decreasing at each successive marker. A page number that decreases relative to the previous marker (a regressive/out-of-order page sequence) makes the entire map untrustworthy → `AMBIGUOUS` with reason `"non_monotonic_page_markers"`, before any segment is produced.
3. Define `page_at(position) -> int | None`: the page number of the marker with the greatest offset that is `<= position`, or `None` if no such marker exists (i.e., `position` precedes every marker in the document).
4. For a boundary match with body span `[start, end)` (start = the match's own start offset; end = the next match's start offset, or `len(markdown)` for the last match): `page_start = page_at(start)`; `page_end = page_at(end - 1)`. Both are resolved from the document-wide map, independent of whether a `[[Pág. N]]` marker happens to fall inside `[start, end)` at all.
5. If `page_at(start)` is `None` (no marker anywhere at or before this boundary's own start — the boundary's page context is genuinely unresolvable from the document), the outcome is `AMBIGUOUS` with reason `"unresolved_page_context"`. Because `end > start` always holds for a non-empty match span and the map's offsets are monotonic, `page_at(end - 1)` cannot fail once `page_at(start)` has succeeded (the same or a later marker will resolve it); no separate empty-body/no-marker-in-slice check is needed or performed.
6. **Removed:** the former Decision 3(b) requirement that "each resulting segment must contain at least one `[[Pág. N]]` marker" (`empty_segment_body`) is retired as a general-purpose ambiguity check for the `segments` outcome. A segment's body legitimately containing zero markers of its own (because it shares a page with, or is a sub-record within, a page whose marker precedes it) is not itself a defect — it is the expected shape for same-page multi-record boundaries. The single remaining necessary check is `page_at(start) is None` (step 5 above), which is strictly narrower and only fires when page context is truly unresolvable (e.g., a boundary occurring before the very first marker in the entire document), not merely absent from one segment's own slice.
7. `SINGLE` outcome is unaffected by this decision: the whole-document case already resolves `page_start`/`page_end` from every marker found anywhere in the document (`min`/`max` over the full marker set), which was already correct positional behavior and needs no correction.
8. `Segment.body` is unchanged: it remains the exact contiguous literal slice `markdown[start:end]`, unmodified, with no marker inserted, duplicated, or removed. Two or more segments may report the same `page_start`/`page_end` while each retaining a disjoint, non-overlapping, byte-exact body slice — sharing a page number is not sharing content.

**Why:** This is the direct architectural fix requested: page context is a positional fact about *where in the document* a boundary occurs, established once from the document's own marker map, never inferred from what characters happen to land inside one arbitrarily-sliced body, from the previous segment's resolved page, from assumed sequential counting, from a number found in body text, from the source filename, or from any LLM/OCR step. It also correctly captures the "segment starts on page 4 and continues into page 5" shape (`page_start=4, page_end=5`) as a legitimate outcome distinct from "two segments sharing page 4" (`page_start=page_end=4` for both) — both arise naturally from the same `page_at()` query applied consistently, with no special-cased "inherit previous segment's page" rule anywhere in the implementation.

**Alternatives considered:**
- *Segment inherits the previous segment's `page_end` when its own slice has no marker* — explicitly rejected per user instruction: this is a content-blind heuristic that happens to produce the right answer for adjacent same-page records but has no positional grounding and would silently mis-attribute a segment that starts on a *later* page than its predecessor ended, if a future corpus shape ever violated the "always same or next page" assumption.
- *Keep `empty_segment_body` as-is and special-case "same page as neighbor" separately* — rejected: adds a second, redundant ambiguity mechanism (structural neighbor-lookup) on top of the one already-correct positional mechanism (the document-wide map), increasing the chance the two disagree; the positional map alone is sufficient and strictly more general.
- *Requiring every segment to carry a synthetic `[[Pág. N]]` marker inserted at its own body's first character when none is present* — rejected outright: this would fabricate a marker that Phase 1 never emitted at that exact literal position, violating the immutability of the body slice and the project's standing rule against inventing page markers.

### Decision 8 — Boundary detection and identity resolution share one canonical structural parser for `precedentes-qualificados-tema-repetitivo-v1` (post-1ter finding, same change)

**What actually happened:** orchestrator validation after Task 1ter's page-map correction re-ran `producer analyze` against the real `output/STJ - Precedentes Qualificados.md` file and found that, although `segment_markdown()` now correctly recognizes all 10 real `Tema Repetitivo` headers (Decision 2bis's corrected separator forms) and produces 10 correctly page-bounded segments, `resolve_segment_identity()` in `legal_segment_identity.py` still resolves every one of them as `requires_operator_metadata`. Root cause: `legal_segment_identity.py` defines its own independent regex (`_OWN_PRECEDENT_HEADER`), authored before Decision 2bis's real-corpus correction, that only accepts the originally-specified two-ASCII-space separator at both field boundaries — it was never updated to accept the corpus-evidenced U+E205-flanked form at the first boundary. Boundary detection (`legal_source_segmentation._PRECEDENT`) and identity extraction (`legal_segment_identity._OWN_PRECEDENT_HEADER`) had silently diverged into two independent structural definitions of the same real-world header shape, one corrected and one not. This is a structural-consistency defect, not a data/corpus defect: the two modules must agree on what a valid `Tema Repetitivo` header *is*, by construction, not by keeping two hand-synchronized copies of the same regex.

**Correction adopted (structural, not cosmetic):** the two field-boundary separator forms from Decision 2bis (`<SEP1>`: two ASCII spaces OR space+U+E205+space; `<SEP2>`: two ASCII spaces OR one ASCII space) are extracted into exactly one canonical, capturing structural pattern, `PRECEDENT_HEADER_PATTERN`, defined once in `legal_source_segmentation.py` (the module that owns the corpus-evidenced structural anchor per Decision 2/2bis) and exported for reuse:

```python
PRECEDENT_HEADER_PATTERN = re.compile(
    r"^Tema Repetitivo (\d+)(?: {2}| \ue205 )Situação "
    r"([^\s\ue205](?:[^\r\n\ue205]*?[^\s\ue205])?)(?: {2}| )"
    r"Órgão (\S(?:[^\r\n]*\S)?)$",
    re.MULTILINE,
)
```

- `legal_source_segmentation.py`'s boundary detector uses this same compiled pattern via `match.start()`/`match.group(0)` exactly as before (its capturing groups do not change match-span or boundary behavior; only enable reuse).
- `legal_segment_identity.py` imports `PRECEDENT_HEADER_PATTERN` from `legal_source_segmentation` (no dependency inversion: identity already depends on segmentation for `Segment`; this adds one more import from the same already-permitted direction) and uses `match.group(1)` (record number) / `match.group(2)` (situação value) directly against the segment's own `body`, replacing the old hand-duplicated `_OWN_PRECEDENT_HEADER` regex entirely. `_OWN_PRECEDENT_HEADER` is deleted, not kept as a second definition.
- No new normalization, no `\s+`/`.*` widening, no symmetry requirement between `<SEP1>`/`<SEP2>` is introduced — the accepted literal forms are exactly Decision 2bis's, now expressed and consumed from one place instead of two.
- Identity extraction continues to operate only on the segment's own `body` (never boundary metadata, never `segment_id`/`source_unit_label`); an internal citation to a different `Tema Repetitivo` number elsewhere in the same body still does not match this anchor unless it independently satisfies the complete three-field shape on its own physical line, and per Decision 5/6 the segment's resolved identity is never taken from anything but its own header occurrence(s).
- Fail-closed behavior (Decision 3, Decision 2bis) is unchanged: a truncated/incomplete header at either boundary still does not match `PRECEDENT_HEADER_PATTERN` at all and is handled by the existing missing-field/`AMBIGUOUS` paths in `resolve_segment_identity()`, not by a separate identity-only fallback.

**Why:** This is the literal fix for "a fronteira estrutural e a identidade jurídica do conceito são coisas diferentes, mas devem compartilhar a mesma definição estrutural quando se referem ao mesmo objeto real" — boundary detection and identity extraction are different *operations* (finding a split point vs. reading a value) over the *same* structural fact (a `Tema Repetitivo` record header), and a change to the corpus-evidenced shape of that fact (Decision 2bis) must not be able to update one operation's understanding of it while leaving the other stale. A single exported, capturing regex removes the possibility of the two ever silently diverging again; any future corpus-evidenced separator-form correction is now a one-place edit.
**Alternatives considered:**
- *Duplicate the corrected regex into `legal_segment_identity.py` again, this time with the U+E205 form added* — rejected: this is exactly the pattern that caused the defect (two independently maintained copies of one structural fact); it would fix today's finding while leaving the same divergence risk for the next corpus correction.
- *Move all boundary-detection regexes into `legal_segment_identity.py`* — rejected: violates Decision 1's module boundary (segmentation owns structural/boundary concerns; identity resolution owns type-specific canonical field extraction) and would make `legal_source_segmentation.py` depend on identity resolution, inverting the dependency direction Decision 1 established (segmentation is a leaf module).
- *Introduce a generic "structural header registry" abstraction shared across all rule types* — rejected as over-engineering for this finding: only one structural anchor (`precedentes-qualificados-tema-repetitivo-v1`) currently needs identity-field extraction from its own header; a single exported pattern constant is the smallest correct fix, and a broader abstraction can be introduced later if/when a second rule needs the same treatment.

Real-corpus re-validation of `output/AIRESP-1833684-2020-02-12.md` (via `producer build --type Jurisprudencia`, `segment=None`/`SINGLE` path, unaffected by this change) confirms the same finding already on record before Task 1quater: `ConceptCandidate.render_text()` (the value `producer build` emits as `candidate` and the same value `producer publish` writes via `write_atomic`) ends with exactly one trailing `\n`. The already-published file at `bundle/jurisprudencia/stj_agint_no_recurso_especial_no_1833684_sc.md` (written by an earlier, unmodified `publish` run, not touched by this change) ends with two trailing newline characters (`\n\n`) — one byte longer than the freshly rendered candidate. ### Decision 10 — Identity extraction must analyze the segment's own pre-marker prefix, not only text after its first internal `[[Pág. N]]` marker (post-1quater finding, same change)

**What actually happened:** orchestrator validation after Task 1quater's shared-parser correction re-ran `producer analyze` against the real `output/STJ - Precedentes Qualificados.md` file and found that 6 of the 10 real segments resolve correctly (978, 999, 1014, 1016, 1039, 1065) but 4 (692, 731, 954, 1031) still resolve `identity_status: requires_operator_metadata` for `repo_jur_tribunal`. Root cause, confirmed by direct offset-level inspection of `_deterministic_extract()` in `legal_semantic_review.py`: the function's page-splitting step (`re.finditer(r"\[\[Pág\. \d+\]\]", markdown)`) only ever produces page text starting *after* a marker found inside the string it receives; when no marker precedes the first marker inside that string (i.e., the string itself begins mid-page), the entire substring preceding that first internal marker is discarded and never becomes part of any `(page_num, page_text)` tuple `_deterministic_extract()` iterates over. This is invisible for the whole-document call (`_deterministic_extract(artifacts.markdown)`) because Phase 1 always starts the whole document at its own first `[[Pág. N]]` marker, so there is never a non-empty prefix to lose. It is also invisible for segments whose header happens to be the very first thing after a `[[Pág. N]]` marker already present in the document maps to the segment's own start position exactly (e.g. Tema 978/1039, whose slice starts immediately after a marker) or where the segment's `repo_jur_tribunal` evidence happens to also appear after the first *internal* marker (e.g. Tema 999/1014/1016/1065). But for Tema 692/731/954/1031, the segment's `body` begins with the header line and several paragraphs of genuinely-owned prose — including the segment's own STJ/STF tribunal mentions — *before* the first `[[Pág. N]]` marker contained in that particular slice (because that marker belongs to the *next* physical page the segment's content continues onto). `_deterministic_extract(segment.body)` silently drops that entire prefix (up to several KB of the segment's own content, confirmed by direct length measurement) before running any field-extraction regex, so `repo_jur_tribunal` (and potentially other fields) are searched for only in the truncated remainder, not the segment's genuine, complete body.

**Correction adopted (structural, not cosmetic):** `_deterministic_extract()`'s internal page-splitting helper is corrected so that any non-empty substring preceding the first `[[Pág. N]]` marker found *inside the string it receives* is treated as a legitimate leading page-text entry, not discarded:

1. Compute `matches = list(re.finditer(r"\[\[Pág\. \d+\]\]", markdown))` exactly as today (unchanged regex, unchanged scope: only markers inside the received string are ever read — no reaching outside `Segment.body`, no reading the source document's marker map from within this function).
2. If `matches` is empty, behavior is unchanged (`pages = [("1", markdown)]`) — this already covers the segment-with-zero-internal-markers shape (Decision 7's Tema 978/1039 case) correctly today and needs no change.
3. If `matches` is non-empty and `matches[0].start() > 0`, prepend one leading page-text entry covering `markdown[:matches[0].start()]` (the genuine prefix) *before* the entries already derived from each marker's own `match.end()` to the next marker/EOF. This entry's page-number label is supplied by an explicit, optional keyword-only parameter `leading_page: str | int | None = None` on `_deterministic_extract()`; every existing whole-document call site (`legal_semantic_review.py`'s own `review()`, `legal_producer.py`, `legal_producer_cli.py`'s publish-time Legislacao check) is unaffected because it never needs to pass this parameter (no observable behavior change there — the prefix in a whole-document call is always empty because Phase 1 always starts at `[[Pág. 1]]`, so this new branch is inert for every existing call site). `legal_segment_identity.py::resolve_segment_identity()` is the only call site that gains a value: it now passes `leading_page=segment.page_start` when given a `Segment` (a value already computed and validated by `legal_source_segmentation.py`'s document-wide `page_map`/`page_at()` from Decision 7 — reused by explicit contract, not recomputed) — no synthetic `[[Pág. N]]` marker is ever inserted into `body`; only the page-text/page-number *tuple* used for field extraction and `page_refs` metadata gains this one extra leading entry. When `leading_page` is not supplied and a genuine prefix exists, the entry's page-number label falls back to the string form of the first *internal* marker's own page number (`matches[0].group(1)`) — a label, never a fabricated marker — so the fallback path still analyzes 100% of the received text even without a caller-supplied `leading_page`.
4. All existing pages derived from markers strictly *inside* the received string are computed exactly as before (unchanged loop, unchanged `match.end()`/next-`match.start()` slicing) and are appended *after* the new leading entry, preserving reading order — no duplication, no re-slicing of any character already covered by an existing page-text span.
5. Every deterministic extraction rule downstream (`tema_occurrences`, tribunal detection, `PRECEDENT_HEADER_PATTERN` reuse in `legal_segment_identity.py`, etc.) is unaffected in its own logic — they already iterate `pages` positionally/in order and pick "first occurrence" or "distinct-values-across-all-pages" per field; they now simply see one additional, genuinely-owned page-text entry instead of silently never seeing that text at all. No new normalization, no widening of any extraction regex, no new special-casing of segment vs. whole-document analysis inside those rules.
6. A single citation to a different tribunal appearing inside the segment's own prefix (e.g. a footnote referencing `Tema 799/STF` inside a segment whose own header and majority evidence support `STJ`) does **not** by itself flip or override an already-unambiguous own-tribunal resolution — this is unchanged, pre-existing "first occurrence wins" / conflicting-value-detection behavior in `_deterministic_extract()`'s tribunal loop (`break` on first STJ/STF match per page, in page order) and in `resolve_segment_identity()`'s `AMBIGUOUS`-on-conflict check; the correction here only ensures the prefix *participates* in that already-existing evidence evaluation, it does not change how conflicting evidence across the (now-complete) body is adjudicated.

**Why:** This is the direct, smallest-possible fix for "todo caractere dentro do `Segment.body` pertence ao segmento" applied specifically to the one remaining code path (`_deterministic_extract()`'s internal page-splitting) that was still silently discarding legitimately-owned segment content — not because the content was outside `Segment.body` (it never was), but because a helper written for a document that always starts at its own first marker was reused unchanged for a slice that does not have that guarantee. Reusing the segment's already-computed `page_start` (Decision 7's `page_map`/`page_at()`) for the leading entry's label, rather than fabricating a synthetic marker or re-deriving page context from scratch, keeps this a one-place, contract-respecting fix with no second parallel pagination mechanism.

**Alternatives considered:**
- *Prefix the segment's own `[[Pág. {page_start}]]` marker literally into `body` before calling `_deterministic_extract()`* — rejected outright: fabricates a marker Phase 1 never emitted at that literal position, mutates the very `Segment.body` Decision 5/7 guarantee as an exact, unmodified, contiguous slice, and directly violates the task's explicit prohibition on synthetic markers.
- *Read backward from the segment's start offset into the full source document to find the "real" preceding marker and copy that page's text in* — rejected: reads outside `Segment.body`'s own offsets, reintroducing exactly the cross-segment leakage risk (adjacent segment content) Decision 5's segment-isolation guarantee forbids; the segment's own prefix already contains 100% of the content that legitimately belongs to it, nothing needs to be fetched from outside it.
- *Have `resolve_segment_identity()` special-case "if the body doesn't start with a marker, manually search the whole body without page-splitting at all"* — rejected: this would create a second, parallel, ad hoc extraction code path solely for segments, duplicating `_deterministic_extract()`'s per-type field logic (violating Decision 1/8's "one canonical structural parser"/"no duplicate extraction logic" precedent) instead of fixing the one shared helper both call sites already use.
- *Change `_page_range()`/`page_at()` in `legal_source_segmentation.py` instead* — rejected: those already correctly resolve `page_start`/`page_end` per Decision 7; the defect is specifically in `legal_semantic_review.py::_deterministic_extract()`'s independent, page-splitting-for-field-extraction helper, which never consulted the document-wide page map to begin with (it only ever looked at markers inside whatever string it was handed) — fixing it there is the minimal, correctly-scoped change.

### Decision 11 — PrecedenteVinculante tribunal resolution requires own-evidence (post real-corpus finding, same change)

Before this subtask, the required real-corpus command reported 10 segments: 9 `resolved` and Tema 954 `requires_operator_metadata` (`missing_identity_fields:repo_jur_tribunal`). Those results came from `_deterministic_extract()`'s generic tribunal scanner, which uses substring/first-occurrence matching per page and could therefore select a court mentioned only in a cross-reference or satellite process.

For `PrecedenteVinculante` only, `repo_jur_tribunal` now means the issuer or institution responsible for this segment's own official precedent. The generic extraction still runs for the other fields, but its tribunal value is replaced by a pure scan of the complete `Segment.body`. Valid own evidence is: (A) `Tema N/STJ|STF` where N equals the number extracted from this segment's canonical header; (B) a structural self-reference joining the court and this unnumbered present theme/matter, such as “o julgamento do tema pelo STJ” or “Superior Tribunal de Justiça ... no presente Tema Repetitivo”; or (C) an institutional organ performing a management/decision act on this record, with no different Tema number as the act's object (or with this record's own number). Cross-references (`Vide`, `Controvérsia`, `Repercussão Geral Tema N/TRIB`), loose citations, and `Processo STF|STJ` mentions never resolve tribunal alone.

Exactly one court supported by own evidence resolves; none requires operator metadata; genuine own evidence for both STJ and STF is ambiguous. Physical mention order is irrelevant. `_deterministic_extract()` is deliberately unchanged for `Jurisprudencia`, `TemaJuridico`, and `Legislacao`: its substring/first-occurrence behavior is recorded as separate architectural debt and is outside this final authorized subtask.

### Decision 12 — Document trailer boundary for `precedentes-qualificados-tema-repetitivo-v1`

The real Tema 1065 segment previously extended to EOF and absorbed document-wide UI/provenance/address text after its legitimate “Última atualização: 07/11/2025” line. The precedent segmentation rule now has an optional end-boundary detector. It cuts the last segment at the unique action line `Exportar todos Imprimir todos Imprimir selecionados` only when that line is immediately followed (allowing blank-line whitespace) by the institutional provenance sentence beginning `Esta pesquisa recupera informações inseridas pelo NUGEPNAC` and containing `Secretaria de Jurisprudência do STJ. Versão X.Y.Z.W | de ...`.

The detector is scoped only to `precedentes-qualificados-tema-repetitivo-v1`, searches after the final record boundary, and requires exactly one complete two-anchor match. If the pair is absent, partial, duplicated, or out of position, no trailer cut occurs and the last segment remains the exact slice to EOF. The retained body is still `markdown[start:end]`; no normalization or synthetic page marker is introduced, and `page_end` is recomputed positionally from `end - 1`.

## Risks / Trade-offs

- **Risk:** Two shipped rules are corpus-specific in their exact regex shape (STJ bulletin formatting). Mitigated: the registry itself is generic and versioned; adding rule N+1 for a new bulletin shape does not touch `legal_source_segmentation.py`'s core logic or any existing rule, only adds a new registry entry plus its own tests/evidence — matching the task's "extensões determinísticas por tipo/fonte" requirement.
- **Risk:** A real corpus item might partially match a rule (e.g., OCR noise breaks one dated line) and unexpectedly flip to `AMBIGUOUS` rather than `SEGMENTS`. Mitigated: fail-closed is the explicit, required behavior — a human is alerted rather than a bad split occurring silently.
- **Risk:** `--all-segments` in `build` produces one operational record per segment under the same execution id / provenance sha, which slightly changes `_candidate_gate()`'s lookup-by-provenance logic (it currently assumes one build record per input hash informs one candidate). Mitigated: `_candidate_gate` already scans *all* matching records and only needs "at least one PASS/PASS_WITH_WARNINGS for this provenance", which remains true regardless of how many segment-scoped build records share that provenance; this is verified by an added regression test rather than assumed.
- **Trade-off:** The operator now performs an explicit two-step workflow (`analyze` then `build --segment SEGMENT_ID` / `--all-segments`) for multi-unit sources instead of one `build` call. This is a deliberate trade-off mandated by the task (no silent multi-publish, full operator visibility) over the previous single-step convenience — which was actively producing wrong output.
- **Risk:** Requiring `identity_status: resolved` before building means a genuinely valid concept whose type-specific extraction rules simply haven't been written yet for that shape (rather than the concept truly lacking identity) will incorrectly block as `requires_operator_metadata`. Mitigated: this is the same class of limitation the existing whole-document `_deterministic_extract()` already has (extraction is inherently incomplete-by-design and improved incrementally); segmentation does not make this worse, and blocking is the safe default vs. publishing under a fabricated identity.

## Migration Plan

No data migration; no existing bundle concepts are affected (this change only touches `build`/`analyze`, never `publish`, against real corpus fixtures; validation is read/build-only). Existing `SINGLE`-outcome tests and real-corpus fixtures (`AIRESP-1833684-2020-02-12`, `L10.406_CC_2002`) are re-run as regression evidence and must show byte-identical candidate output to before this change.

## Open Questions

None blocking implementation. Decision 6 above is the definitive, documented finding on whether "Jurisprudência em Teses" edições map to `TemaJuridico`: they do not, under the current OKF profile, and this change does not implement a workaround for that gap.
