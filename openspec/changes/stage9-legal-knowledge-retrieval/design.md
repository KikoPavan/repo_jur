## Goals / Non-Goals

**Goals:**

- implement the read-only Legal Knowledge Retrieval capability over `repo_jur/bundle/`: concept-level lexical index + sync/rebuild + fingerprint stale detection; Lexical-First, Hybrid-Ready search execution (structured filters → candidate discovery → canonical materialization → Retrieval Contract result envelope); Direct Read-Only Filesystem Search fallback; Structural Block-First, Page-Aware, Size-Profiled chunking with a versioned Chunking Profile; Optional/Conditional/Profile-Governed/Fail-Open reranking seam disabled by default;
- prove with executable tests the FROZEN invariants: Zero-Write over `bundle/` (index/sync/rebuild/search never mutate the bundle; bundle byte-identical after any retrieval operation); `concept_id` positional identity and canonical join key (no Stable IDs, no frontmatter duplication); canonical materialization rejects stale derived text; relevance and trust remain separate (no automatic boost/demote/exclusion); provenance envelope exact (1-PDF vs 2+PDF hash cardinality, `page_refs`/`source_refs` never invented); rebuild leaves the bundle unchanged; no process-storage traversal; no shared Legal/Process index;
- add the minimal additive `repo-jur retrieval sync|rebuild` and `repo-jur search|search-diagnose` CLI surface with deterministic exit codes and full CLI non-regression (`converter-juridico`, `repo-jur route`, `repo-jur producer`, `repo-jur process` untouched);
- keep the semantic/vector boundary a **disabled future seam**: no embedding model, vector DB, ANN/HNSW, RRF, fusion, or reranker implementation is selected, invoked, or required; SQLite FTS5 is a reference Implementation Choice, not an architecture requirement;
- keep retrieval observability content-safe and outside `bundle/` and outside Phase-1 artifacts.

**Non-Goals:**

- Judicial Process Retrieval in any form (explicitly deferred to a separate future contract — `decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`; `retrieval-contract-v2.8-FROZEN.md` §1A; impl-plan §11);
- semantic/vector search activation; selecting an embedding model, vector DB, ANN/HNSW, RRF, or fusion algorithm;
- selecting or invoking any reranker implementation/model/provider (disabled default; fake adapter only);
- modifying Domain Router semantics, `router.py` page-level routing, the converter, OCR provider, thresholds, cleaner, validator, report generation, Stages 2–8 code, `contracts.py`, `config.py` existing fields, or any FROZEN authority;
- introducing Stable Concept IDs / Stable Chunk IDs / `_v2` / automatic `status` mutation / automatic trust-relevance blending;
- writing to `bundle/` or process-domain storage by any retrieval component; creating any shared Legal/Process index;
- Stage 10 (Conformance/Regression) or any Stage-10-or-later work;
- adding or changing dependencies; creating a new FROZEN memo inside this change;
- automatic Git commit/push/merge/archive.

## Decisions

### 1. One OpenSpec change for Stage 9, with C9.1–C9.4 as dependent task groups

Stage 9 has exactly one bounded context in scope — Legal Knowledge Retrieval — because the FROZEN corpus normatively excludes Judicial Process Retrieval from the current retrieval baseline (`decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`; `retrieval-contract-v2.8-FROZEN.md` §1A; impl-plan §11; arquitetura §8.5/§11.65–67). Multiple OpenSpec changes are therefore not required by normative necessity, and splitting purely for implementation convenience is prohibited by the task brief. Following the established repo practice (Stage 7 = one change with C7.1–C7.3; Stage 8 = one change with C8.1–C8.3), this change ships as **`stage9-legal-knowledge-retrieval`** with four dependent task groups: C9.1 lexical index + sync/rebuild, C9.2 search execution + materialization + fallback, C9.3 chunking + Chunking Profile, C9.4 reranking seam. Dependencies: C9.2→C9.1, C9.3→C9.1, C9.4→C9.2 (matches planning backlog §H).

### 2. New `retrieval/` package with flat modules; reuse every existing contract; never touch Stages 2–8 modules

New modules live in `src/pipeline_juridico/retrieval/` (`__init__.py`, `index.py`, `search.py`, `materializer.py`, `fallback.py`, `chunking.py`, `reranking.py`, `config.py`-adjacent `RetrievalConfig` in the existing `config.py`) plus an additive `retrieval_cli.py` registered on `domain_router_cli.py`. Reuse as-is: `ensure_outside_canonical_bundle`, `write_atomic`, `hashing`, contracts. No existing module behavior is modified; the only touch to an existing file is the additive registration on the `repo-jur` entry (Decision 11) and the additive `RetrievalConfig` (Decision 4). Physical-layout memo and impl-plan §0 mandate `REUSE → ADAPT IN PLACE → TEST` and forbid parallel trees for existing capabilities.

### 3. Stage 9 input contract: the canonical bundle only, read-only; never Phase-1 artifacts, reports, or process storage

Retrieval's source of truth is `repo_jur/bundle/` concept documents produced by the closed Stage 7 Legal Producer — the only authorized publication path (arquitetura §8.11). The chunker operates on the **current canonical concept body materialized from the bundle**, never on Phase-1 intermediate output (chunking memo §14.1: "A saída intermediária da Fase 1 não é source of truth para chunking de retrieval"). Eligibility rule: a file is indexable if and only if it is a non-reserved `.md` concept document under `bundle/` (reserved `index.md`/`log.md` are navigation/audit files, not concepts — `concept-identity-physical-structure-v1.3` §1.2); non-Markdown files under `bundle/` are never indexed. Process-domain storage, Phase-1 artifacts, and technical reports are never traversal targets (tests enforce no process-storage path resolution and no report parsing).

### 4. Derived-data root: `var/retrieval/` (HR-4), configurable, gitignored, outside `bundle/`

The derived root hosts the lexical index, optional chunk sets, and retrieval observability records. Approved location (HR-4): `var/retrieval/` — consistent with the existing `var/routing/state` and `var/object-storage/` operational roots and already outside the canonical tree. `RetrievalConfig` (additive to `config.py`) validates the root through `ensure_outside_canonical_bundle`, rejects `bundle/`-resolving values, and supports environment override following the existing config conventions. An additive `.gitignore` entry (`var/retrieval/*`) is added only for the derived root (HR-4); the canonical `bundle/` is deliberately NOT gitignored (canonical corpus is Git-tracked per arquitetura §7 classification). If the derived root is ever moved outside the worktree, the `.gitignore` entry is inert and harmless.

### 5. Chunking Profile v1: versioned profile with HR-2-approved numeric defaults

The FROZEN corpus freezes the chunking **model** (Structural Block-First, Page-Aware, Size-Profiled; literal contiguous spans; interval-derived `page_refs`; forced split only when needed; no Stable Chunk ID) but explicitly defers all numeric values to a versioned Chunking Profile (chunking memo §3.5/§8.5; tech-spec §6.5/§11.4). The v1 profile shape is fixed: `profile_version`, `measurement_unit`, `soft_limit`, `hard_limit`, `forced_split_overlap`, with invariants `soft_limit > 0` and `hard_limit > soft_limit`. **HR-2 APPROVED the v1 numeric defaults**: `measurement_unit=characters`, `soft_limit=6000`, `hard_limit=12000`, `forced_split_overlap=200`. These are versioned, configurable profile defaults — NOT permanently frozen constants. Any future numeric change requires a new Chunking Profile version and/or configuration fingerprint and MUST invalidate/rebuild the affected derived chunk and index state (§11.7, §13.3; the Chunking Profile configuration participates in `chunk_set_fingerprint` and `index_config_fingerprint` validity). Profile change never touches the bundle or the lexical index content.

### 6. Chunk-set persistence: persist during `retrieval sync` (HR-3)

The concept-level lexical index is the only persistent index required for the initial search path (search-execution memo §8.1; retrieval-contract §13.3/§14.8). Chunk sets are a derived representation available for future semantic capabilities. **HR-3 APPROVED persistence during `retrieval sync`**: the chunker runs during `retrieval sync` and persists derived chunk sets (with `chunk_set_fingerprint`, `chunk_ordinal`, `body_range`, `page_refs`, `section_path`/`table_header_context`) under the derived root, versioned by Chunking Profile + chunker logical version, so chunk-set validity is independently checkable and rebuildable without touching the bundle. Persisted chunk sets remain fully rebuildable derived data and never become canonical authority; compute-on-demand at materialization is NOT the v1 behavior.

### 7. Stale-index runtime policy: degrade to Direct Read-Only Filesystem Search with observable degraded condition (HR-6)

When the index is absent, incompatible, stale-without-sync-opportunity, corrupt, unavailable during rebuild, or failing initialization, the runtime degrades to the normative **Direct Read-Only Filesystem Search** fallback (search-execution memo §10; retrieval-contract §13.4; tech-spec §10.3). HR-6-approved v1 policy: at query time the runtime checks index validity (fingerprint + schema + logical + config versions); if invalid it records an operational degraded/stale condition in retrieval observability and falls back to filesystem search for that query — it does **not** block the query and does **not** silently serve stale text. Fallback does not promise index-level ranking/performance equivalence and the degraded mode is observably signaled (tech-spec §10.3). Canonical correctness is preserved in fallback: `concept_id` from the current path, frontmatter read from the concept, provenance per Retrieval Contract.

### 8. Structured-filter vocabulary: mandatory minimum + explicitly retrieval-relevant Legal OKF Profile fields, declared in a retrieval schema (HR-5)

Retrieval Contract §7 + tech-spec §10.4 mandate filters on `type`, `status`, `tags` and forbid making every `repo_jur_*` field automatically filterable; the Legal OKF Profile marks a specific set of fields retrieval-relevant. The PUBLIC Stage-9 v1 filter vocabulary is exactly the 15 keys `type`, `status`, `tags`, `lei_numero`, `lei_ano`, `lei_esfera`, `lei_tipo`, `processo_numero`, `tribunal`, `relator`, `data_julgamento`, `ramo_direito`, `precedente_numero`, `precedente_status`, `tema_numero`. The internal Legal OKF Profile frontmatter fields keep their canonical `repo_jur_*` naming; the retrieval layer deterministically maps each public key to its canonical frontmatter field — for the 12 retrieval-relevant profile fields the public key is the canonical field name with the `repo_jur_` prefix stripped (`lei_numero` → `repo_jur_lei_numero`, `tribunal` → `repo_jur_tribunal`, …), and `type`/`status`/`tags` map to the identically-named canonical keys. This internal mapping is NOT a public alias: `repo_jur_*` spellings are NOT accepted as additional public filter keys in Stage 9 v1 and no aliases are added. The vocabulary is declared in a versioned retrieval schema/config (never inferred from content); unknown filter keys — including `repo_jur_*` supplied as public filter names — are configuration errors. No automatic status boost/demote/exclusion is introduced; filter values are used only as explicitly requested filters.

### 9. Canonical materialization is a hard pre-delivery invariant

Before any result reaches the consumer, the materializer must (tech-spec §10.5): receive the candidate `concept_id`, confirm the current path exists in the bundle, read the current canonical frontmatter/body, validate required provenance, and reject stale candidate text as authority. A stale/missing candidate is never silently presented: the runtime records an operational stale condition and either re-queries/syncs or degrades to filesystem search. The delivered `text_content` is always materialized from (or validated against) the current canonical bundle content — this is the defense against stale derived text becoming final evidence (search-execution memo §11; retrieval-contract §13.5).

### 10. Result envelope follows Retrieval Contract §4–§5 exactly

Universal: `concept_id` + `text_content`. Conditional: `source_refs` when the concept declares sources (per-trecho attribution only when explicitly sustained; never invented); `page_refs` only when the physical-page association is explicit and unambiguous (cross-page chunks carry all related pages; never chosen by character majority); exactly 1 PDF → `source_pdf` + `repo_jur_pdf_hash`; 2+ PDFs → `source_refs` preserving `sources[].id` + `repo_jur_pdf_hashes` mapping; `repo_jur_pdf_hash` and `repo_jur_pdf_hashes` never coexist. `trust_tier` (derived from `verified`) is optional derived metadata; `repo_jur_verification_history` is never exposed as active trust/ranking input. No invented page→source or trecho→source association is ever emitted.

### 11. Operational CLI: additive `retrieval` group + `search`/`search-diagnose` on the `repo-jur` entry (HR-7)

Per tech-spec §14 the repo-local operational surface is `repo-jur retrieval sync`, `repo-jur retrieval rebuild`, `repo-jur search "<query>"`, `repo-jur search-diagnose "<query>"`. The retrieval subcommand group and the search commands are registered **additively** in `domain_router_cli.py` (the `repo-jur` entry point — where `producer`/`process`/`route` already live); `cli.py` (the `converter-juridico` entry) is never touched. Conventions: argparse, environment-driven directories (`RETRIEVAL_STATE_DIR`/derived-root env following the existing pattern), deterministic exit codes (0 success, 1 input, 2 unexpected, 3 config/contract, 5 blocked — matching the existing CLI family), sanitized logging (no secrets, no full document content, no full critical identifier values), atomic writes for observability records, and `sync`/`rebuild`/`search` never writing to `bundle/`. `search-diagnose` exposes candidate discovery, filter application, materialization, fallback, and reranking states for operational diagnosis without changing result semantics.

### 12. Search result limits: validated v1 limits only — pagination explicitly out of scope (HR-8)

Retrieval Contract §12 requires limits to protect the consumer context window. **HR-8 APPROVED**: the v1 default result limit is 10 and the v1 maximum limit is 50, both configurable via `RetrievalConfig`, validated (`limit ≤ max`) and never silently exceeded. **Pagination is NOT part of Stage 9 v1**: cursors, page tokens, offset-based paging, and snapshot-paging semantics are explicitly OUT OF SCOPE and deferred to a future authorized change, because cursor/snapshot/rebuild consistency semantics are not yet normatively defined — v1 invents no such semantics and the search interface/CLI exposes no pagination surface. Reranking candidate-pool limits belong to the Reranking Profile (tech-spec §6.7) and are separate from consumer result limits.

### 13. Reranking seam: interface + disabled default + fail-open + relevance/trust separation

The seam exposes `should_rerank(query, candidates, profile)` and `rerank(query, candidates, profile)` (tech-spec §12.1). Default profile `enabled: false`; when disabled, the pipeline is candidate discovery → structured filtering → canonical materialization → result assembly (reranking memo §6.1). When enabled and triggered, a failure/timeout/unavailability: discards partial/invalid reranker output, preserves the previous valid order, records `failed_fallback`, and continues to canonical materialization (reranking memo §15.4) — never silent. Observability states: `disabled`, `bypassed`, `applied`, `failed_fallback` (reranking memo §15.8). Prohibited: automatic relevance multipliers from `trust_tier`, `verified`, `status`, `repo_jur_verification_history`, or temporal decay; reranking never removes or deprecates candidates and never writes to the bundle/index/frontmatter. No mandatory intent classifier (tech-spec §12.3).

### 14. No semantic/vector infrastructure; SQLite FTS5 is a reference Implementation Choice only

No embedding model, vector DB, ANN/HNSW, RRF, or fusion algorithm is selected or enabled (search-execution memo §6.3–§6.4; retrieval-contract §13.6; impl-plan §11). SQLite FTS5 via stdlib `sqlite3` is a valid reference lexical backend (tech-spec §10.2, §19) and the recommended v1 implementation, but the architecture binds to the `LexicalIndexBackend` interface (`build`/`sync`/`search` — tech-spec §10.1), so another compatible backend can be substituted without touching the bundle, schemas, Retrieval Contract, `concept_id`, or the result interface. The semantic candidate seam (`semantic_candidates(query, filters)`) is an interface future boundary that remains disabled/non-normative in v1. The Markdown structural parser for chunking is an Implementation Choice (tech-spec §11.2) with a chunker logical version participating in chunk-set validity.

### 15. Determinism, rebuildability, and technology neutrality are tested invariants

For identical canonical inputs, Chunking Profile, and chunker/indexer logical versions, chunk generation and index records are deterministically equivalent (chunking memo §3.6; retrieval-contract §10). A full rebuild discards derived lexical/chunk state, traverses the current bundle, recreates derived data, and never writes into `bundle/` (tech-spec §13.5; acceptance §17.23). The contract does not require byte-identical index binaries or scores across engines (retrieval-contract §10) — determinism is asserted at the record/span level, not at float/serialization level.

## Risks / Trade-offs

- **Stale derived text becoming final evidence** → Mitigation: canonical materialization is a hard pre-delivery invariant (Decision 9) with dedicated tests (stale index, missing candidate, content update, rename/move); fallback keeps canonical correctness (Decision 7).
- **Chunking Profile drift** → Mitigation: profile version + configuration fingerprint + chunker logical version + `chunk_set_fingerprint` participate in chunk-set/index validity; any numeric change requires a new profile version and/or config fingerprint and invalidates/rebuilds the affected derived chunk and index state (Decision 5/6; tech-spec §13.3).
- **Reranking overreach** → Mitigation: disabled default, fail-open, relevance/trust separation, observability states, fake-adapter-only tests (Decision 13; tech-spec §12).
- **Path pollution / derived data leaking into Git** → Mitigation: `var/retrieval/` under `ensure_outside_canonical_bundle` + additive `.gitignore` entry (Decision 4).
- **Filter vocabulary bloat / silent semantic filters** → Mitigation: versioned retrieval schema declaring exactly the approved retrieval-relevant keys; unknown keys are configuration errors; no content-derived filters (Decision 8).
- **Index staleness at query time** → Mitigation: fingerprint-based stale detection (content_fingerprint + schema/logical/config versions) and observable degraded fallback (Decision 7; tech-spec §13.1).
- **Accidental coupling to Stage 7/8 producer semantics or Domain Router** → Mitigation: source-inspection tests asserting the retrieval modules import no producer, no router, no converter, no OCR, no LLM/semantic client, and no process-storage path; bundle byte-identity tests after every retrieval operation.
- **Semantic seam scope creep** → Mitigation: `semantic_candidates` remains an unimplemented interface boundary; no embedding/vector code is written in v1 (Decision 14).

## Open Questions (future, non-blocking)

- **FTS5 tokenizer choice** (C9.1 design-time; tech-spec §19 allows implementation freedom): the v1 tokenizer (e.g. unicode61 with PT-BR-friendly settings vs. trigram) is an Implementation Choice that affects recall for legal identifiers (CNJ masks, law numbers). Recommended: start with `unicode61` + explicit numeric/identifier handling per the Exact Retrieval Capability (search-execution memo §3.1), calibrate against the real corpus in implementation.
- **Reranking trigger-policy details** (C9.4 design-time; tech-spec §12.3): the trigger policy (`mode`) is profile-governed; v1 ships `mode: disabled` (and optionally a deterministic bypass for exact-identifier queries as an allowed optimization, not a universal rule).
- **Chunk-level lexical indexing**: explicitly NOT introduced by this change; the concept-level index remains the initial search path (retrieval-contract §14.8). A future semantic/hybrid change may propose chunk-level candidates under a separate authorized contract.
- **`repo_jur_verification_history` exposure**: audit-only if exposed at all; never active trust/ranking input (Retrieval Contract §4.3/§13.7). No v1 decision changes this.
