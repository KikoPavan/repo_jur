## Why

Stages 1–8 are closed and archived. The FROZEN corpus requires the last producer-side stage: **Stage 9 — Legal Knowledge Retrieval**, consuming the canonical `repo_jur/bundle/` produced by the closed Stage 7 Legal Producer (`implementation-plan-repo-jur-v1.1-FROZEN.md` §11; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §10–§13, §18 Stage 9; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §5.3/§5.4, §8.5, §11 invariants 27–46, 65–67; `retrieval-contract-v2.8-FROZEN.md`; `decision-memo-search-execution-path-v1.0-FROZEN.md`; `decision-memo-chunking-strategy-v1.0-FROZEN.md`; `decision-memo-reranking-pipeline-v1.0-FROZEN.md`; `decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`). The repository currently contains no retrieval, index, chunking, or search component (verified 2026-08-23: `src/pipeline_juridico/` has no retrieval module; `bundle/` does not exist yet; no retrieval tests exist), so Stage 9 must create that capability — strictly read-only over the canonical bundle, strictly downstream of canonical publication, and strictly bounded to the Legal Knowledge context.

## What Changes

- Add the Stage 9 **Legal Knowledge Retrieval** capability as the read-only consumer of `repo_jur/bundle/`: a concept-level lexical candidate index with sync/rebuild and fingerprint-based stale detection; a Lexical-First, Hybrid-Ready search execution path (structured filters → candidate discovery → canonical materialization → Retrieval Contract result envelope) with a normative Direct Read-Only Filesystem Search fallback; a Structural Block-First, Page-Aware, Size-Profiled derived chunker governed by a versioned Chunking Profile; and an Optional, Conditional, Profile-Governed, Fail-Open reranking seam whose default is `enabled: false` (`retrieval-contract-v2.8-FROZEN.md` §13–§15; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §10–§13; `implementation-plan-repo-jur-v1.1-FROZEN.md` §11).
- Index **only** canonical Legal Knowledge concept documents under `repo_jur/bundle/` (the four type trees `legislacao/`, `jurisprudencia/`, `temas/`, `precedentes/` per `concept-identity-physical-structure-v1.3-FROZEN.md` §1.1), never Phase-1 artifacts, never technical reports, never Judicial-Process storage, and never any intermediate output.
- Enforce the FROZEN retrieval invariants: **Zero-Write** over `bundle/` (absolute read-only; derived data lives outside `bundle/` and is gitignored if inside the worktree); `concept_id` as the canonical join key (positional, never duplicated in frontmatter, no Stable IDs); canonical materialization before any result is delivered (index/chunk stale text never becomes final evidence); relevance and trust as separate dimensions (no automatic boost/demote/exclusion by `status`, `trust_tier`, `verified`, or `repo_jur_verification_history`); and the Retrieval Contract provenance envelope (`concept_id` + `text_content` universal; `source_refs`/`page_refs`/`source_pdf`/`repo_jur_pdf_hash`/`repo_jur_pdf_hashes` conditional and never invented).
- Add the operational retrieval CLI surface recommended by tech-spec §14 — `repo-jur retrieval sync`, `repo-jur retrieval rebuild`, `repo-jur search "<query>"`, `repo-jur search-diagnose "<query>"` — registered additively on the existing `repo-jur` entry point (`domain_router_cli.py`), following the established CLI conventions (argparse, environment-driven directories, deterministic exit codes, sanitized logging, atomic writes, content-safe observability), leaving `converter-juridico`, `repo-jur route`, `repo-jur producer`, and `repo-jur process` untouched.
- Add retrieval observability as operational/technical artifacts only, outside `bundle/` and outside Phase-1 artifacts: index fresh/stale/degraded, sync/rebuild events, reranking states `disabled|bypassed|applied|failed_fallback`, and canonical-materialization stale/missing conditions (tech-spec §15.1).
- Keep **Judicial Process Retrieval out of scope**: it requires a separate future contract (`decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`; `retrieval-contract-v2.8-FROZEN.md` §1A; `implementation-plan-repo-jur-v1.1-FROZEN.md` §11; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §11 invariants 65–67). No shared index, no shared chunk schema, no Legal/Process fusion is created by this change.
- Do not modify Domain Router semantics (`openspec/specs/domain-router/spec.md`; `src/pipeline_juridico/domain_router.py`), do not modify closed Stage-7 or Stage-8 producer semantics, do not modify `router.py` page-level routing, do not modify any FROZEN authority, and do not implement Stage 10 (Conformance/Regression).

## Capabilities

### New Capabilities

- `legal-knowledge-retrieval`: Defines the Stage 9 bounded-context capability covering read-only retrieval over the canonical Legal Knowledge bundle — a concept-level lexical candidate index (reference implementation choice: SQLite FTS5) with sync/rebuild and fingerprint-based stale detection; a Lexical-First, Hybrid-Ready search execution path (structured filters, candidate discovery, canonical materialization, Retrieval Contract result envelope, Direct Read-Only Filesystem Search fallback); Structural Block-First, Page-Aware, Size-Profiled derived chunking with a versioned Chunking Profile; and an Optional, Conditional, Profile-Governed, Fail-Open reranking seam (disabled by default). It indexes only canonical `repo_jur/bundle/` concept documents, never mutates the bundle or Phase-1 artifacts, never touches Judicial-Process storage, never introduces embeddings/vector infrastructure/LLM rerankers, and preserves `concept_id` positional identity, provenance fidelity, relevance/trust separation, and deterministic, rebuildable derived data.

### Modified Capabilities

None. The existing `contract-harness`, `itp-ingress-preflight-evidence`, `shared-conversion-core`, `critical-data-validation`, `phase1-quality-gate`, `domain-router`, `legal-knowledge`, `judicial-process`, and `juridical-pdf-conversion` requirements are not changed by this proposal.

## Impact

- Primary affected code (planned): new `src/pipeline_juridico/retrieval/` package (`index.py` with the SQLite FTS5 reference backend, `chunking.py`, `reranking.py`, `search.py`, `materializer.py`, `fallback.py` per the Repository Implementation Map in `design.md`), new `src/pipeline_juridico/retrieval_cli.py` (or equivalent per design Decision 11), additive `RetrievalConfig` in `config.py`, an additive `.gitignore` entry for the derived-data root (only if the derived root resolves inside the worktree), and new `tests/test_retrieval_*.py` files. No existing module behavior is modified; the additive registration of the `retrieval` subcommand group and the `search`/`search-diagnose` commands happens on the existing `repo-jur` entry only.
- Inputs consumed: `repo_jur/bundle/` concept documents produced by the closed Stage 7 Legal Producer (the only authorized publication path). No Phase-1 artifact, technical report, or process-domain artifact is a retrieval input.
- New operational surface: `repo-jur retrieval sync|rebuild` and `repo-jur search|search-diagnose` (exact flag surface in design Decision 11; command naming is Implementation Choice per tech-spec §14).
- No new dependency: SQLite FTS5 (stdlib `sqlite3`), the Markdown structural parser, and the filesystem fallback are Implementation Choices; no vector DB, embedding model, LLM, reranker, external service, or storage provider is introduced (impl-plan §11; tech-spec §19).
- Stages 8/10 remain out of scope and are not coupled to by this change; Judicial Process Retrieval remains explicitly deferred to a separate future contract.

## Non-Goals

- Implementing **Judicial Process Retrieval** in any form (index, chunk schema, search, reranking, or shared infrastructure) — explicitly deferred to a separate future contract by FROZEN authority.
- Activating semantic/vector search: no embedding model, vector DB, ANN/HNSW, RRF, or fusion algorithm is selected or enabled; the semantic candidate seam remains a future, disabled, non-normative boundary.
- Selecting or invoking any reranker implementation: the seam is testable with a fake adapter but no neural/LLM reranker is required; the default is `enabled: false` and fail-open.
- Modifying the Domain Router semantics, `router.py` page-level routing, the converter, OCR provider, cleaner, validator, report generation, Stages 2–8 code, `contracts.py`, or any FROZEN authority (`docs/baselines/frozen/*`).
- Introducing Stable Concept IDs, Stable Chunk IDs, `_v2` suffixes, automatic `status` mutation, or automatic boost/demote/exclusion by `status`/`trust_tier`/`verified`/`repo_jur_verification_history`.
- Writing to `repo_jur/bundle/` by any retrieval component; writing derived data into `bundle/`; writing process-domain storage; creating any shared Legal/Process index.
- Implementing Stage 10 (Conformance/Regression) or any Stage-10-or-later work.
- Exposing pagination, cursors, page tokens, offset-based paging, or snapshot-paging semantics in Stage 9 v1 — explicitly deferred to a future authorized change (HR-8).
- Adding or changing dependencies; creating a new FROZEN memo inside this change.
- Automatic Git commit/push/merge/archive as part of retrieval operation.

## Residual Risks

1. **Stale derived text becoming final evidence.** The index and chunks are derived; the FROZEN mitigation is mandatory canonical materialization against the current bundle before delivery, plus fingerprint-based stale detection and the Direct Read-Only Filesystem fallback. This change makes materialization a hard invariant with dedicated tests (tech-spec §10.5, §17.22; retrieval-contract §13.5).
2. **Chunking Profile numeric values are versioned v1 defaults, not FROZEN constants.** The FROZEN corpus explicitly defers `soft_limit`, `hard_limit`, `measurement_unit`, and `forced_split_overlap` to a versioned Chunking Profile calibrated on real corpus (chunking memo §3.5/§8.5; tech-spec §6.5/§11.4). HR-2 approved the v1 defaults `measurement_unit=characters`, `soft_limit=6000`, `hard_limit=12000`, `forced_split_overlap=200`; any future numeric change requires a new Chunking Profile version and/or configuration fingerprint and invalidates/rebuilds the affected derived chunk and index state by design.
3. **Derived-data root placement.** If the derived root resolves inside the Git worktree it must be gitignored (retrieval-contract §9/§10; arquitetura §7 row 6). The approved location is `var/retrieval/` (HR-4); the `.gitignore` addition is limited to the derived root and never touches `bundle/`.
4. **Stale-index runtime policy.** Tech-spec §10.5 permits either sync-then-query or degrade-to-filesystem-fallback with an observable stale condition at query time; the approved v1 policy is degrade-to-filesystem-fallback with an observable degraded condition, never blocking the query (HR-6).
5. **Result-limit defaults.** Retrieval Contract §12 requires limits to protect the consumer context window; the concrete defaults are operational parameters (HR-8), not FROZEN values. HR-8 approved default 10 / maximum 50; pagination, cursors, page tokens, and snapshot-paging semantics are explicitly OUT of scope for Stage 9 v1 and deferred to a future authorized change.
6. **Filter vocabulary beyond the minimum.** Retrieval Contract §7 mandates `type`, `status`, `tags` and forbids making every `repo_jur_*` field filterable; the Legal OKF Profile marks additional fields retrieval-relevant. The v1 filter vocabulary is a schema/config decision (HR-5) that must not silently expose non-authorized fields.
7. **Retrieval never becomes a Producer.** The boundary is enforced by contract: retrieval consumes the bundle read-only, publishes nothing, and does not alter canonical publication authority (arquitetura §8.11; impl-plan §11).

## Human Review Decisions (HR-1..HR-8 — Human-Approved 2026-08-23)

- **HR-1 — Stage-9 bounded-context scope (APPROVED)**: Stage 9 covers **Legal Knowledge Retrieval only** over `repo_jur/bundle/`; **Judicial Process Retrieval remains explicitly out of scope** and deferred to a separate future contract (`decision-memo-retrieval-bounded-context-scope-v1.0-FROZEN.md`; `retrieval-contract-v2.8-FROZEN.md` §1A; `implementation-plan-repo-jur-v1.1-FROZEN.md` §11; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §11 invariants 65–67) — preserved, not broadened.
- **HR-2 — Chunking Profile v1 numeric values (APPROVED)**: the versioned Chunking Profile v1 defaults are `measurement_unit=characters`, `soft_limit=6000`, `hard_limit=12000`, and `forced_split_overlap=200`. These are versioned, configurable profile defaults, NOT permanently frozen constants: any future numeric change requires a new Chunking Profile version and/or configuration fingerprint and MUST invalidate/rebuild the affected derived chunk and index state — see design Decision 5.
- **HR-3 — Chunk-set persistence scope in v1 (APPROVED)**: derived chunk sets ARE persisted to the derived-data root during `retrieval sync`. They remain fully rebuildable derived data and never become canonical authority; the concept-level lexical index remains the only persistent index and chunking is a derived representation for future semantic capabilities — see design Decision 6.
- **HR-4 — Derived-data root location and `.gitignore` (APPROVED)**: derived retrieval state lives under `var/retrieval/` (consistent with the existing `var/routing/state` and `var/object-storage/` operational roots) and is gitignored via an additive `.gitignore` entry, only if it resolves inside the worktree; canonical `repo_jur/bundle/` remains Git-tracked and is the sole Legal Knowledge source of truth — see design Decision 4.
- **HR-5 — Retrieval-relevant filter vocabulary (APPROVED)**: the PUBLIC Stage-9 v1 retrieval filter vocabulary is exactly the 15 keys `type`, `status`, `tags`, `lei_numero`, `lei_ano`, `lei_esfera`, `lei_tipo`, `processo_numero`, `tribunal`, `relator`, `data_julgamento`, `ramo_direito`, `precedente_numero`, `precedente_status`, `tema_numero`, declared through a versioned retrieval schema/config and never inferred from content. The internal Legal OKF Profile frontmatter fields retain their canonical `repo_jur_*` naming (e.g. `repo_jur_lei_numero`, `repo_jur_tribunal`); the retrieval layer deterministically maps each public key to its canonical frontmatter field — for the 12 retrieval-relevant profile fields the public key is the canonical field name with the `repo_jur_` prefix stripped, and `type`/`status`/`tags` map to the identically-named canonical keys. That internal mapping is NOT a public alias: `repo_jur_*` spellings are NOT accepted as additional public filter keys in Stage 9 v1, unknown filter keys — including `repo_jur_*` supplied as public filter names — are configuration errors, and no aliases are added. Filtering does not imply automatic trust/status/verification boost or demotion — see design Decision 8.
- **HR-6 — Stale-index runtime policy (APPROVED)**: when the index is absent/stale/incompatible/corrupt, query execution degrades observably to Direct Read-Only Filesystem Search with an observable degraded/stale condition; queries must not silently use stale derived text as authority and must not auto-mutate canonical content; the query is never blocked on an automatic sync — see design Decision 7.
- **HR-7 — Operational CLI surface (APPROVED)**: additive `repo-jur retrieval sync|rebuild` and `repo-jur search|search-diagnose` commands on the existing `repo-jur` entry point only (never `converter-juridico`), with deterministic exit codes, environment-driven derived root, and no write path to `bundle/`; existing converter, producer, process, and route behavior remains non-regressed — see design Decision 11.
- **HR-8 — Search result limits and pagination (APPROVED WITH SCOPE REDUCTION)**: v1 search limit defaults to 10 with maximum 50 (context-window protection per Retrieval Contract §12), both validated configuration values. Pagination is NOT part of Stage 9 v1: cursors, page tokens, offset-based paging, and snapshot-paging semantics are explicitly deferred to a future authorized change and must not be invented in v1 — see design Decision 12.
