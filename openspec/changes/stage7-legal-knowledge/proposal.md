## Why

The FROZEN architecture requires the Stage 7 Legal Knowledge Pipeline: the `legal_knowledge` branch of the Stage 6 Domain Router, composed of the Legal Semantic Review / Enrichment layer followed by the Legal Producer, publishing exclusively into `repo_jur/bundle/` (`implementation-plan-repo-jur-v1.1-FROZEN.md` §9; `technical-implementation-spec-repo-jur-v1.2-FROZEN.md` §3.3, §3.5, §8C, §9, §18 Stage 7; `arquitetura-fase2-repo-jur-v15-FROZEN.md` §1.2, §1.4, §4, §11 invariants 47–67; `decision-memo-semantic-review-enrichment-layer-v1.1-FROZEN.md`). Stage 6 is closed: the Domain Router deterministically produces exactly one of `legal_knowledge`, `judicial_process`, `review_required` (`openspec/specs/domain-router/spec.md`; `src/pipeline_juridico/domain_router.py`), and `guard_legal_bundle_write` already reserves the Legal bundle for the `legal_knowledge` domain (`src/pipeline_juridico/contracts.py:119-136`). No component in the current repository produces a Legal concept candidate, runs a Legal Semantic Review, writes OKF frontmatter, resolves legal identity/provenance, or publishes to `repo_jur/bundle/` — the entire legal_knowledge branch is unimplemented (verified 2026-08-22: `src/pipeline_juridico/` contains no semantic-review, no producer, no OKF/YAML, no bundle-write path outside the guard itself; `bundle/` does not exist yet). Stage 7 must therefore create that branch: the Legal Semantic Review seam and the Legal Producer, both domain-isolated, deterministic-where-FROZEN-demands, and bound by the immutable Phase 1 artifacts.

## What Changes

- Add the Stage 7 Legal Knowledge Pipeline as the `legal_knowledge` branch of the closed Stage 6 Domain Router: a Legal Semantic Review / Enrichment seam followed by a Legal Producer, both consuming only conformant Phase 1 artifacts (literal Markdown + technical conversion report carrying `result.quality_gate`) whose recorded gate outcome is `PASS` or `PASS_WITH_WARNINGS` and whose routing decision is exactly `legal_knowledge`. Unconverted input, raw PDFs, `judicial_process`-routed artifacts, `review_required`-routed artifacts, and gate-`FAIL` artifacts SHALL NOT enter the Stage 7 boundary (mirrors the Stage 6 input contract; `phase1-operational-spec-v1.1-FROZEN.md` §14 — Producer receives only `PASS`/`PASS_WITH_WARNINGS`; `arquitetura-fase2` §1.4/§8.9).
- Reuse the existing shared contracts without modification: `Phase1Artifacts`, `RouteTarget`, `CriticalValidationStatus`, `Actor`, `GateState`, `guard_legal_bundle_write` (`src/pipeline_juridico/contracts.py`), `config.py::ensure_outside_canonical_bundle`, `validator.py::write_atomic`, `hashing.py` — the physical-layout memo and impl plan §0/§1 mandate `REUSE → ADAPT IN PLACE → TEST` and forbid parallel trees and duplication (`decision-memo-physical-layout-logical-capability-mapping-v1.0-FROZEN.md`; `implementation-plan-repo-jur-v1.1-FROZEN.md` §0, §13).
- Create the Legal Semantic Review seam: a bounded-context-specific engine (`legal-semantic-review`) whose input is the immutable Phase 1 Markdown plus the technical report, and whose output is a `ReviewResult` carrying structured patches (`before`/`after`/`reason`/`confidence`/`page_refs`/`evidence_refs`), extracted fields, classification suggestions, warnings, and the `REVIEW_REQUIRED` signal — per the FROZEN semantic-review memo and design doc §20 (tech spec §8C; `decision-memo-semantic-review-enrichment-layer-v1.1-FROZEN.md`; `docs/Pipeline_Conversao_Juridica_Corrigido.md` §20.3/§20.4). The layer SHALL NOT publish, SHALL NOT overwrite Phase 1, and SHALL preserve every original word on structural operations. Deterministic (non-LLM) structural review rules are versioned and registry-backed, mirroring the Stage 4 rule-provenance discipline; any AI/semantic engine is adapter-based, engine-neutral, and explicitly authorized — never silent LLM classification (task invariant; tech spec §3.5, §19; arquitetura §1.4).
- Create the Legal Producer: the only component authorized to publish concepts into `repo_jur/bundle/` (tech spec §9.1; arquitetura §4, §8.11; impl plan §1.2/§9). It consumes the Phase 1 artifacts (read-only) plus the ReviewResult and a validated producer context, resolves identity/provenance (PDF cardinality, sources, duplicate-act handling per `decision-memo-duplicate-act-handling-v1.0-FROZEN.md`), applies the lifecycle/field-ownership merge (10-step FROZEN workflow; `lifecycle-field-ownership-v1.4-FROZEN.md` §4), renders an OKF concept document per the Legal OKF Profile (`legal-okf-profile-v1.3-FROZEN.md`), validates OKF + profile + cardinality + ownership, and publishes atomically through `guard_legal_bundle_write` into the positionally-named concept path under `bundle/` (`concept-identity-physical-structure-v1.3-FROZEN.md` §1–§5). Publication obeys: no automatic `verified`, no automatic `status`, no `_v2` suffix, `generated.at` only on meaningful change, atomic write + Git-diff exposure, no automatic commit/push (tech spec §9.5–§9.8; arquitetura §4).
- Add a minimal operational `repo-jur producer` CLI surface following FROZEN §14 (`repo-jur producer build/validate/publish`) and the existing CLI conventions (argparse, environment-driven directories, sanitized logging, deterministic exit codes, atomic writes), with the existing `converter-juridico` and `repo-jur route` surfaces untouched (CLI non-regression).
- Add Producer observability as operational/technical artifacts only (tech spec §15.1 Producer events: resolution outcome, human-review requirement, materiality decision category, publication result), stored outside `/bundle/` and outside Phase 1 artifacts, content-safe.
- Do not implement Stage 8 (Judicial Process), Stage 9 (Retrieval), any later stage, or any Judicial-Process storage/index; do not modify Domain Router semantics; do not modify FROZEN authorities.

## Capabilities

### New Capabilities

- `legal-knowledge`: Defines the Stage 7 bounded-context capability covering the Legal Semantic Review / Enrichment seam and the Legal Producer for the `legal_knowledge` branch of the Domain Router. It consumes only conformant Phase 1 artifacts (gate `PASS`/`PASS_WITH_WARNINGS`, route `legal_knowledge`) read-only, produces structured review patches that preserve every original word, renders Legal OKF concept candidates per the Legal OKF Profile, resolves identity/provenance and duplicate acts conservatively, applies lifecycle/ownership merge, validates OKF + profile + cardinality, and publishes atomically into `repo_jur/bundle/` exclusively through `guard_legal_bundle_write` — without mutating Phase 1, without semantic content rewrite, without silent LLM classification, without Judicial-Process behavior, and without automatic `verified`/`status`/versioning.

### Modified Capabilities

None.

The existing `contract-harness`, `itp-ingress-preflight-evidence`, `shared-conversion-core`, `critical-data-validation`, `phase1-quality-gate`, `domain-router`, and `juridical-pdf-conversion` requirements are not changed by this proposal.

## Non-Goals

- Implementing Stage 8 (Judicial Process Semantic Review / Producer / storage) or any Judicial-Process retrieval; `judicial_process`-routed artifacts are out of the Stage 7 boundary by contract.
- Implementing Stage 9 (Legal Knowledge Retrieval) — the bundle is produced here, retrieval is a later stage consuming it.
- Modifying the Stage 6 Domain Router semantics, `router.py` page-level routing, the converter, OCR provider, routing thresholds, cleaner, validator, report generation, Stage 2–6 code, `contracts.py`, or `config.py`.
- Modifying any FROZEN authority (`docs/baselines/frozen/*`).
- Introducing semantic/LLM classification silently: any AI/semantic review engine must be explicitly authorized, adapter-based, and engine-neutral; the deterministic path is the default.
- Automatic publication authority beyond the Legal Producer: no component other than the Legal Producer may write `bundle/`; no automatic Git commit/push/merge/archive.
- Automatic `verified` fabrication, automatic `status` mutation, `_v2`/UUID/stable-id creation (CLOSED decisions preserved).
- YAML/enrichment schema reuse across bounded contexts (Legal and Process schemas remain isolated — shared-conversion-core memo *Prohibited Coupling*).
- Implementing or validating deterministic redundant-value comparison (future capability per arquitetura §1.6, critical-data spec).
- Adding or changing dependencies; writing to `bundle/` outside the Producer; writing process-domain storage.

## Residual Risks

1. **Semantic review engine choice is open.** The FROZEN corpus authorizes the semantic review *layer* (memo v1.1; design doc §20.4) but the model/prompt/provider choice is explicitly out of scope of the design doc §20.5 ("Escolha de modelo, prompt ou provedor para o revisor semântico"). This change therefore ships the seam + deterministic rules and leaves any LLM engine as an explicit, adapter-based, opt-in choice to be approved in a separate change (HR-2). If a later change authorizes an LLM engine, the deterministic invariants (word preservation, patches, REVIEW_REQUIRED, no publication authority) still constrain it.
2. **`type` classification authority is not FROZEN-defined.** The OKF profile makes `type` producer-owned and mandatory, but no FROZEN baseline says how `legal_knowledge`-routed content is classified as `Legislacao`/`Jurisprudencia`/`TemaJuridico`/`PrecedenteVinculante`. Stage 6 explicitly denied `legal_hints` routing authority (HR-1, archived). This change proposes explicit operator intent in the producer context as the deterministic source, with any semantic classification suggestion non-authoritative (HR-3). If the reviewer prefers a different authority (e.g. deterministic rule from report metadata), that is a human decision to record before implementation.
3. **The Critical-Data Validation status is not recorded in the Phase 1 report** (Stage 4 seam result is not wired into `report.py`). The Stage 6 router receives it as an explicit parameter; Stage 7 inherits the same input shape: the Legal Producer boundary is reached only after the router emitted `legal_knowledge`, which itself already required gate `PASS`/`PASS_WITH_WARNINGS` and critical status `OK`/`WARNING` (domain-router spec precedence). Stage 7 re-reads the recorded gate outcome from the report (structural enforcement) and does not depend on a non-existent critical-status field.
4. **The bundle does not exist yet.** `repo_jur/bundle/` is absent (verified 2026-08-22). The Producer must create the canonical tree (`bundle/{legislacao,jurisprudencia,temas,precedentes}/`) on first publication, and the tests must exercise the guard against a real bundle root. `bundle/` is deliberately NOT gitignored (canonical corpus is Git-tracked per arquitetura §7 classification); the Producer writes only concept documents, never derived/runtime data.
5. **`sources[].resource` provenance threading is not FROZEN-defined.** The OKF profile requires `sources[].resource` to identify the preserved evidence when the concept derives from identifiable sources, and the ingestion contract stores the preserved evidence reference in the ingress state (`ingress.py::_write_state` — `result` = evidence reference URI), but the Phase 1 technical report itself does not carry the resource URI (only `input.sha256` + `execution_id`). The Producer must therefore receive the preserved-evidence reference through the validated producer context (or a deterministic derivation the reviewer approves — HR-4), never inventing a resource.
6. **`generated.at` semantics require a deterministic "meaningful change" test.** FROZEN requires `generated.at` to change only on meaningful content change and forbids timestamp-only diffs (`lifecycle-field-ownership-v1.4` §5). The implementation must define the meaningful-change predicate deterministically (content/ownership/provenance change vs. pure re-run) and test it; an overly loose predicate risks spurious diffs, an overly strict one risks hiding legitimate updates.
7. **Duplicate resolution touches legal identity, where the FROZEN rule is deliberately conservative.** `decision-memo-duplicate-act-handling-v1.0` forbids reducing duplicate handling to `same hash → no-op` and requires HUMAN REVIEW on material change or ambiguity. The implementation must implement the full resolution state machine (physical identity → logical resolution → NO-OP/controlled update/distinct concept/HUMAN REVIEW) with the write blocked on ambiguity; the deterministic part is implementable, but the "safe equivalence" judgment boundary is a human decision (HR-5) that the tests must keep conservative (no automatic consolidation without safe equivalence).

- Primary affected code (planned): new `src/pipeline_juridico/legal_semantic_review.py`, new `src/pipeline_juridico/legal_producer.py`, new `src/pipeline_juridico/legal_producer_cli.py`, new `tests/test_legal_semantic_review.py`, `tests/test_legal_producer.py`, `tests/test_legal_producer_cli.py`, and the additive registration of the `producer` subcommand group on the existing `repo-jur` console entry (`domain_router_cli.py`) — the single permitted touch on an existing module, via a subcommand-dispatched entry or equivalent per design Decision 9; no existing module behavior is modified and the `route` surface and `converter-juridico` remain byte-identical.

## Human Review Decisions Required

- **HR-1 — Deterministic-first scope for the Semantic Review seam**: whether Stage 7 v1 ships the semantic review as a deterministic, rule-registry-backed seam (recommended: yes; AI/LLM engine deferred to a future authorized change) — see design Decision 4.
- **HR-2 — No LLM engine in Stage 7 v1**: confirm that no model/provider/prompt for a semantic/LLM review engine is selected or invoked in this change; the seam stays engine-neutral and the deterministic path is default (design doc §20.5 out-of-scope preserved) — see design Decision 4.
- **HR-3 — `type` classification authority**: confirm that the deterministic source of the OKF `type` is the explicit operator intent carried in the validated producer context (`--type Legislacao|Jurisprudencia|TemaJuridico|PrecedenteVinculante`), with any semantic classification suggestion non-authoritative and conflicting suggestions routed to `REVIEW_REQUIRED`; no content-derived `type` inference — see design Decision 5.
- **HR-4 — Preserved-evidence reference threading**: confirm the `sources[].resource` for PDF-derived concepts is supplied through the validated producer context (the preserved evidence reference), matched against `input.sha256` from the report, and never invented; derivation from the ingress state record by execution id is the deterministic alternative if preferred — see design Decision 6.
- **HR-5 — Duplicate resolution conservatism boundary**: confirm that the deterministic duplicate-resolution state machine blocks all writes on ambiguity/material change (HUMAN REVIEW), never reduces to `same hash → no-op`, and that the "safe equivalence" judgment for automatic consolidation is never made by content inference in v1 — see design Decision 7.
- **HR-6 — Operational CLI surface and write semantics**: confirm the `repo-jur producer build|validate|publish` surface (FROZEN §14 recommendation), that `build`/`validate` never write to `bundle/`, that `publish` is the single write path through the guard, and that no automatic Git commit/push is introduced — see design Decision 9.
